# Get a deploy through the Vercel build

A push to `main` goes two ways at once (since 2026-11-08, case `2026-09-29-github-actions-test-gate`). GitHub Actions run the whole Jest suite (`.github/workflows/tests.yml`: four parts on four runners, then one closing check «Tests»), and Vercel builds the app without tests (`npm run build` in `frontend/` is `node scripts/build-production.js`: Next and the type check). Vercel's Deployment Checks (Settings → Build and Deployment → Deployment Checks: «Tests», GitHub, Production) keep a built production deployment off the domain until «Tests» of its commit is green. One red test keeps the site on the version before it; one type error fails the Vercel build. Before pushing run the FULL `npm run test:fast`, `npm run lint` and `npx tsc --noEmit`, not only the tests you touched.

## How

- A forward push that changes nothing the app reads is canceled instead of built: `frontend/vercel.json` → `ignoreCommand` runs `frontend/scripts/vercel-ignore-build.sh`, which compares the last successful deployment of the branch (`VERCEL_GIT_PREVIOUS_SHA`) with this commit under `frontend/`, minus the Firestore rules, Firebase CLI config and two notes. It skips only a forward push; any doubt builds: no previous SHA, a redeploy of the same commit, an older commit (redeploy or rollback), history that does not contain the previous deployment, a previous commit outside the shallow clone, a failing `git diff`. It cannot see environment variables: after changing one in Vercel, press Redeploy (a same-commit redeploy builds) — a later docs-only push would be skipped and would NOT ship the new value. After a skipped push the app still shows the previous SHA as its version, because that artifact is what runs; verify a deploy by SHA only for commits that change the app. A new file that neither `next build` nor Jest reads and should not trigger builds goes into the exclude list AND into `frontend/scripts/__tests__/vercel-ignore-build.test.js`. Replayed on the deploys of 2026-09-25..28: 6 of 27 would have been skipped; consecutive deploys were at most 3 commits apart, well inside the depth-10 clone. With 10 or more commits since the last successful deployment the ancestry cannot be proven in the clone and the push builds.
- `frontend/scripts/build-production.js` runs `next typegen` into `.next-typecheck`, then `next build` and `tsc -p tsconfig.build.json --noEmit` side by side; either one failing fails the build.
- `test:ci` is the workflow's Jest run (`--ci`, a failure-only reporter `frontend/scripts/failure-only-jest-reporter.js`, three workers, `--workerIdleMemoryLimit=512MB`), each runner taking `--shard=N/4`; the four parts cover every file once (2026-11-08: 292/292/291/291 of 1166, 13 227 tests, the same count the Vercel build ran). The runners (4 vCPU, 16 GB) are free for this public repository; the first run took 3.5 min against 1015 s of Jest inside the Vercel build the day before, on its 2 vCPU. Node in the workflow follows the Vercel project's Node.js Version (26.x). No run is cancelled by a newer push: a code commit cancelled for a docs-only one (which Vercel does not build) would wait for its check for good. The config's `maxWorkers: '50%'` is for local runs.
- Tests live in two trees, `frontend/__tests__/` and co-located `app/**/__tests__/`. A targeted run, or a truncated `find | head`, misses the second one.
- Time: a CI runner is far slower per core than a laptop, so anything timed is slower there. `configure({ asyncUtilTimeout: 4000 })` in `frontend/jest.setup.js` is the ONE place that decides how long `waitFor` / `findBy*` wait, and `testTimeout: 15000` in `frontend/jest.config.ts` stays above it, so a starved expectation names itself instead of being cut off. `frontend/__tests__/architecture/asyncExpectationsHaveRoom.test.ts` freezes both; it reads the ceiling Jest actually applies from the jest-circus state (a `jasmine` global does not exist under circus). Never pin a shorter window in one test (`{ timeout: 2000 }`): it is the first to run out on a busy machine.
- After async work, wait for the CONDITION (`waitFor`, `findBy*`), never for a guessed number of microtask flushes.
- In CI the suite sees no environment variables at all (no secrets; locally `next/jest` loads `.env.local`). Until 2026-11-08 it ran inside the Vercel build with the production environment. A switch that changes which code path a screen takes must be cleared in `frontend/jest.setup.js` (it deletes `NEXT_PUBLIC_USE_CLIENT_*`, the DataEngine switches, `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, `NEXT_PUBLIC_ENABLE_TEST_LOGIN`). Simulate the build env by setting the variable on a local run, e.g. `NEXT_PUBLIC_DATA_ENGINE_COLLECTIONS=councils DATA_ENGINE_COLLECTIONS=councils npm run test:fast`.
- Watch the tests through the run: `gh run list --limit 3`, `gh run watch <id> --exit-status`; the closing check of a commit: `gh api repos/MykhailoDmytriakha/my-preacher-helper/commits/<sha>/check-runs --jq '.check_runs[] | "\(.name) \(.conclusion)"'`. Watch the build through the commit status, not the deployments list: `gh api repos/MykhailoDmytriakha/my-preacher-helper/commits/<sha>/status` shows the `Vercel` context as `pending` from the start of the build and `success`/`failure` at the end, with the build URL. The `/deployments` list got the entry only when the build finished (2026-09-28: `8359ece9` pending for about ten minutes and absent from that list), so a wait loop on it looks like "no deploy".
- A test that walks the filesystem as a gate must skip what git does not track: `app/dev/` is gitignored and exists on one disk only. Use `applicationFiles` from `frontend/__tests__/architecture/firestoreBoundary.ts`.

## When it goes wrong

- A deployment shows as CANCELED: either the ignore step skipped it — then its log has a `vercel-ignore-build: skip - …` line with the reason — or Vercel dropped it from the queue for a newer commit. To force a build anyway, redeploy it from the dashboard with "Use project's Ignore Build Step" unchecked.
- Built but not on the domain: the commit's «Tests» is red or still running. Read the failing part: `gh run view <id> --log-failed`; a flaky part reruns with `gh run rerun <id> --failed`, and Vercel promotes the deployment once «Tests» turns green.
- Read the failing deployment's own log: `npx vercel inspect <dpl_id> --logs`. Reproduce locally with `npm run build` (Next and the type check), but not while `next dev` runs from the same `.next`; the tests with `npm run test:fast`.
- Green locally, red on the build machine: make the same failure appear locally with a perturbation. Delaying an awaited rejection by 30 ms turned the old assertion red and the fixed one green. If you could not reproduce it, say so plainly; a fix you have not reproduced is a guess.
- `Found multiple elements with the role … and name "<key>"` only on the build machine: the test's i18n mock answers a key with the bare key, so labels that differ in the app by an interpolated value (`{{place}}`) are one name in the test, and a query over a whole window matches several as soon as late content lands. Wait for that content, then query inside the element's own container (`within(line)`), not the window.
- A guard test red on one machine and green on another measured the working copy. Every architecture guard walks the app through `applicationFiles` and `NOT_IN_THE_REPOSITORY` in `frontend/__tests__/architecture/firestoreBoundary.ts`, which skip the gitignored `app/dev/` (fixed 2026-09-29; before that `dataEngineBoundary.test.ts` failed on `dev/...` entries on one disk). A new guard reuses that walk instead of writing its own.

The suite moved to GitHub Actions in four parts (first run 3.5 min, the same 13 227 tests) and Vercel's Deployment Checks wait for its «Tests»; the Vercel build keeps Next and the type check. Case `2026-09-29-github-actions-test-gate`.
- 2026-09-28: deploys had grown from ~5 to 8-14 minutes. All of it was the Jest phase: one worker since 2026-09-16, plus a suite 53 % heavier since then. Measured anatomy and options: `.cases/2026-09-27-data-engine-rollout/data/test-speed-2026-09-28.md`.
- 2026-11-04: deployment of `4e16831c` failed on `analysisHistoryStep.test.tsx`, green locally 16 of 16 under load: a screen a test left mounted took its step a moment after the cleanup, inside the next test, and rewrote that test's entry; the build machine's slow Back then read a step at the list's address. Reproduced by replaying the order in one test; fixed in the code (a late cleanup leaves another screen's entry alone) and in the tests (they settle after cleanup).
- 2026-08-15: the write-interface guard counted gitignored `app/dev/`, and a prayer-modal test flushed one microtask expecting the refusal to have arrived (the build log still showed "Saving..."). The first "fix" hit the wrong test and broke a neighbour; only a control run caught it.
