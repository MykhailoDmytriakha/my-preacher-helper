# Keep a choice on this device

A setting the person makes on one device and finds there again — the marker's colour and last tool, search history — lives in `frontend/app/utils/deviceChoice.ts`. Do not write another store over `localStorage`.

**Should it follow the person to every device and survive lost device storage?** Then it lives in the account: `accountChoice({ part, key, parse, fallback })` (`frontend/app/utils/accountChoice.ts`) has the `deviceChoice` interface plus `useWritable()`. The account's copy is the users document's `reading` field: add the part to `ReadingSettings` (`models/models.ts`) and to the `reading` schema (`data-engine/resourceSchemas.ts`); `reading` is already in the writable list (`data-engine/protocol.ts` — a field missing there is refused on the device before anything is sent). The one bridge is `ReadingSettingsSync` (`providers/UserSettingsProvider.tsx`). The construction, after five Codex rounds on 02.11 (two copies of the truth kept parting somewhere new — another tab, a refused storage write, a version taken back, an account switch): while the bridge is connected the screen shows ONLY the editor's draft of the part, plus the person's changes on their way for that account; `save` hands the editor the CHANGED FIELDS, laid on its copy of the part; `readFresh` is the editor's view too. The device keeps a copy under the account's name (`<key>@<owner>`, drawn only before the editor is heard, taken away once the account is known to lack the part) and reads, never writes, the record of the version before (`<key>`). That record is conservative: shown and moved up only while no account has ever shown this device the part; it moves once, `MOVE_UP_AFTER_MS` after the server answered with none, as no change over the account's copy, and only after `<key>:moved` is written and read back. A part is writable only while its state is known: writer and owner, the editor heard, not while the server's copy of the part (or of `reading`, when the editor has none) waits outside the editor (`document.remote`), and the editor holds the part or the server answered; the bridge adds editor storage keeping and device storage not silent (`isStorageSilent`). Every control uses its store's writable hook (`useTrailPrefsWritable` …). No bridge (a test of a screen, settings not on the engine): a plain device choice. Moved so far (2026-11-02): the trail's settings, cross references, my marks on the text, the analysis help. Tests: `resetAccountChoicesForTests()`, then `connectAccount(owner)`; the bridge with a fake settings document whose `commit` updater gets the editor's newest copy (`__tests__/providers/readingSettingsSync.test.tsx`).

## How

- `const choice = deviceChoice({ key: 'area:name', parse, fallback, onOtherTab? })` once per setting, at module level. `parse(raw | null)` turns the stored text into the setting and gives the defaults for nothing or a broken record; `fallback` is what the server and hydration draw.
- Components read `choice.useChoice()`; code reads `choice.read()`; a change is `choice.save(partial)`, which returns `'kept' | 'memory-only' | 'not-read-back'`. Put a result other than `'kept'` into the technical details (`recordDiagnostic`) — see `components/bible/crossReferencePrefs.ts`.
- A change is built on the newest record: `save(partial)` and every «read, work out, save» caller go through `choice.readFresh()`, which takes storage's record only when its `__savedAt` is newer than the page's (another tab's choice the page never heard of — a tab Safari froze, one in the background). Without it a stale page wrote its older fields back over the newer ones with its next toggle (BUG-20261101-device-choice-stale-page-overwrites: the trail's «Сколько мест хранить» / «Не повторять последние места» went back to the defaults). Draw with `read()` / `useChoice()` only — never `readFresh()`. A change made while storage cannot be read stays in memory (`save` says `memory-only`) and is never written over a record the page has not seen; once storage answers, the next change is laid on that record. A position chosen in the shown copy (the trail's way back, `stepOnTrail`) is found again in the newest record by its content, not by its old index.
- `onFirstRead(found)` says once per page whether storage held a record (`none` · `stored` · `unreadable`); the trail's settings put it into the technical report (`setting`, source `read`), so a choice found as the defaults again shows whether its record was gone or written over.
- Every stored record carries `__savedAt`, the moment of the action by this device's clock. Another tab's record replaces the page's choice only when it is newer, so in ordinary use a queued older event, or a write refused here, does not undo a newer choice. A record without the moment (the earlier version) is followed only by a page that has not chosen yet.
- Limits, accepted for one person with one app window (BUG-20261017-xref-switch-does-not-stay-on): two tabs changing different fields at the same moment can still lose one (each reads the newest record first, then writes); a clock set back plus a late event can misorder; a delayed clear of all storage resets a choice storage refused. Code that reads storage on every render had none of these, and it is what failed on the iPad.
- Tests: `localStorage.clear()` alone does not reset a choice the page already holds — call the store's reset (`resetCrossReferencePrefsForTests`, `resetMarkToolForTests`, or `choice.resetForTests()`) in `beforeEach`. Another tab is a second `deviceChoice` with the same key (it stamps its record), then `window.dispatchEvent(new StorageEvent('storage', { key, newValue: localStorage.getItem(key), storageArea: window.localStorage }))` — without `storageArea` the event is ignored (`__tests__/utils/deviceChoice.test.ts`).
- A value read once when a screen opens and then kept in that screen's state (`components/bible/translation.ts`) does not need the module.

## Why

- 2026-10-17, BUG-20261017-xref-switch-does-not-stay-on: the stores re-read `localStorage` on every render (`useSyncExternalStore` getSnapshot). On the owner's iPad the "Стихи" switch went back to off after a little scrolling or half a minute, three times; the reports showed only "on" saves — no "off", no other tab, no refused write. Desktop WebKit and the simulator held. The module holds the choice in memory from the first read and takes storage again only from another tab's newer record, so nothing but the person's own save or another tab's later choice can change what the screen shows. Two rounds of Codex refutation the same day shaped the rest: a watcher only while a screen is open missed changes; taking an event's value, or storage as it was at the event, let a queued older event undo a newer choice; a failed first read cached as the defaults let the next save overwrite the record.
