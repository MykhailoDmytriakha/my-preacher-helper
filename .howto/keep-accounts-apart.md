# Keep accounts apart on one device

Every store on the device belongs to the device, not to an account, so each one has to name its owner or refuse a foreign one. A leak needs only one layer that forgets; the 2026-10-03 fix found five at once (cross-account entry, BUGS.md history).

## How

- **Identity and restoration.** React readers use `providers/AuthProvider.tsx` (`onAuthStateChanged`) for both the Firebase user and restoration readiness. `useResolvedUid` waits for that provider; an action outside React uses `auth.currentUser` through `resolveOwnerUid`. Anonymous Firebase users are ordinary authenticated sessions. Routes and `~offline/page.tsx` never infer identity from a `guestUser` mirror or the presence of a `firebase:authUser:*` key. Keep `initializeAuth` with the existing `browserLocalPersistence` and popup resolver; do not migrate or clear its store. Wait for Firebase, never a guessed one-second timer. A completed null user means signed out even if obsolete keys remain. No successful login writes an extra identity mirror. Prove existing-session online/offline cold reload, actual SDK cross-tab sign-out, and stale-key negative controls separately from a real Google provider flow (BUG-20260810-auth-mirrors-in-localstorage).
- **Service worker.** `frontend/app/sw.ts` puts private `/api/` reads before the Serwist defaults with `NetworkOnly`; public `/api/share/` remains on its public offline path. Do not reintroduce a shared private response cache. Offline account data belongs to its canonical owner-scoped device store.
- **Data engine reads.** `frontend/app/data-engine/transport.client.ts` checks the owner on every snapshot it accepts — lists, changes and the single-document `read` — with `validateCollectionSnapshots`; a foreign snapshot is `data-loss`. The snapshot store keys `[owner, collection, id]` and validates on read (`snapshots.client.ts`).
- **Firestore SDK cache.** Its IndexedDB persistence is per device. A list query filters by owner, but a single `getDoc` answers offline or on a slow network from the local cache with whatever account last read that id. Every single-document read that reaches a screen passes `ownedBy(owner, document)` (`frontend/app/services/ownerListRead.client.ts`; used by `readOwnerDocument`; `getPrayerRequestById` and `getSermonByIdViaClient` were removed 2026-10-12/13 — prayers and sermons are read through the engine). Reads before a write need no check: the server's rules refuse the write.
- **Query cache lifetime.** `QueryProvider` waits for resolved Firebase identity before opening persistent restoration. Each resolved UID owns a separate QueryClient, mutation cache and persister lifetime; signed-out pages use memory only. `queryPersister.ts` owns both physical-key constructors: `accountQueryCacheKey` retains the legacy input namespace, while `accountReadCacheKey` selects its versioned read-only child. `accountQueryCache.ts` adopts only known legacy key shapes and explicit owners, atomically initializes an absent legacy partition and retains original unknown inputs. Current authored actions belong to the Data Engine; known retired writers remain canonical archival input. Old callbacks and retries keep their captured owner.
- **Independent read-cache records.** Only entitlement/usage and referral-count DTOs currently persist through `accountReadCache.ts`. One owner map is updated atomically through shared `storageUpdate`; a tab skips its unchanged copies and tombstones an omitted observed record only at the same record revision. Whole-cache removal retains a new epoch fence, so an older tab cannot refill it. Per-persister write/remove calls run FIFO and observations advance only after commit ACK. Failed, silent, malformed or future-version reads authorize neither overwrite nor removal. Old global/per-owner inputs remain unchanged; they are not a second active command queue. Compare the exact Firestore snapshot version from `X-Account-Read-Version` when displaying an answer, saving it, and merging a late restore. A retired record retains its last known version, and v2 imports the old offline copy without changing the v1 namespace. The store revision and device clocks serve local storage and presentation only. Generic `createIDBPersister` keeps its existing serializer and unread/late-restore gates through a read/write/remove storage port.
- **Custom device stores and recording drafts.** Capture the owner of the work when it starts, including later transcription failure. `recordingDraftStore.ts` uses that captured owner and its canonical reader/player; do not reassign old unowned files to a new account. A record belongs to its originating operation, not whoever is signed in at a late save. The 2026-10-03 save-time stamping attempt was withdrawn; the current recording lifecycle has a different, tested boundary.
- Prove each layer with a test where another account's copy sits in the store (old key shape and foreign owner) and the server refuses; the screen must not show it.

- **Request identity.** `getAuthenticatedRequestHeaders` captures SDK UID synchronously, then checks the user that supplies the token after the lazy import. Owner-bound calls pass their captured UID; `requestOwnerJson(expectedOwner)` rejects a queued action from another account. A→B→A around an await must never admit B credentials merely because A is current again. The error factories remain shared and re-exported by the owner transport.
- **Failed device reads.** `createIDBPersister` marks input unread before starting I/O. A failed or silent read cannot authorize removal or overwrite, including TanStack's own `removeClient` after rejection. Canonical Engine archival commits first, then atomically retires only exact archived inputs; unknown rows and a newer changed input remain protected. See `.howto/migrate-domain-to-data-engine.md`.
- **Browser files.** Account partitioning protects application publication and replay; it is not encryption of a Chrome profile. Retain offline copies unless a separate retention/security requirement authorizes removal. Access by another person to the same browser profile is a separate owner-context question.

## Do not

- Do not wipe the caches when the owner changes: it was tried and reverted, because it also removed paused offline mutations (unsent edits).
- Do not filter persistence by "the current owner" at write time: before auth restores on boot the owner is unknown, and the first persist would drop the person's own offline cache.

## Why

- 2026-07-25: account B opened A's sermon by direct link and saw A's text from the persisted query cache.
- 2026-10-03: earlier point fixes exposed several stores with different account boundaries. Preserve that lesson: a new key must include its migration, and account changes must not destroy unsent work. Current private worker responses and recording drafts have their own protections; recheck current code before treating historical descriptions as open defects.
