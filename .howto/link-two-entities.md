# Link two entities

For engine-owned collections, use the relation owner through the public engine facade: `useDataMembership()` owns series membership and member creation. `studyMaterials.noteIds` owns material-note membership, with the server deriving reverse note links. `Sermon.sourceNoteIds` owns sermon source-note links through the migrated `useSourceNoteLink` hook. Keep one relationship truth and one action for all affected documents.

## How

- Start a series action with `useDataMembership.begin()` before opening the selector; update its pinned stage, then `save()` one atomic command. For a new sermon/group in a series, use `beginCreate`, `openSeries`, `updateCreation` and one `save()`. Delivery, retry and whole-action discard come from the same hook.
- `studyMaterials.noteIds` is the material membership owner. The engine's `material-notes` relation command updates the material and stages reverse `studyNotes.materialIds` links on the server; consumers must not write the reverse field independently (`frontend/app/data-engine/serverRelations.ts`).
- For sermon source notes, `useSourceNoteLink` takes the engine `useDocumentActions().commit` path when sermons are enabled; `sourceNoteIds` remains the stored owner and `useSermonsBuiltOnNote` derives the other view.
- Forward source views and the source picker read `useStudyNoteDirectory`, which reuses `useStudyNotesEngine` for submitted local rows, normalization and owner fencing. Its `isMissing(id)` delegates to canonical `notePresence(id).kind === 'absent'`; unknown/cache-only IDs and pending local creates/deletes do not certify deletion. Keep source order from `sermon.sourceNoteIds`. A separate React Query/SDK note catalogue cannot see newly accepted offline work. Regression: `app/hooks/__tests__/useSourceNotes.engineRead.test.tsx` compares actual projected rows and local write acceptance; eventual `WriteSubmission.persistence` waits for server ACK and is not an offline capture receipt.
- No mirrored copy on the other side. `sermon.seriesId`, `group.seriesId` and `seriesPosition` are deprecated and ignored by readers; nothing sets them any more except cleanup to `null`. The engine refuses them in an ordinary create or update with `relation-command-required` (`frontend/app/data-engine/serverRelations.ts`), and likewise `series.items`, `sermonIds`, `seriesKind`.

## A linked source is still being created

A saved offline source and the next saved document that references it are ordered work by one preacher. `data-engine/documentReferences.ts` owns live-reference enumeration for documents and immutable commands. `CommitQueue` waits for matching active source creations before preparing consumers; this prevents both premature generation lookup and a permanent server refusal. Runtime uses the same readiness index before delivery, including commands already persisted by an older client. Waiting changes neither the command fingerprint nor the journal result and does not consume an attempt.

- Match owner and the full collection/id. A saved creation remains a prerequisite while its baseline and working copy are absent and its root request is queued/prepared. A pending ordinary update does not delay a new link. Every referenced pending creation must settle; unrelated documents can continue.
- Source ACK lets ordinary preparation continue. Unknown delivery reuses the same source operation and receipt. A genuinely failed or explicitly cancelled source is not manufactured or revived: the consumer proceeds to the existing owner/liveness checks and retains its own words on refusal. Keep the server guards.
- Material membership, sermon source/scratch provenance and final series members reuse the shared reference rules. Atomic participants exclude their own operation; a newly created sermon within a series still waits for an external new source note. Historical unchanged sermon provenance does not acquire a new live-source requirement when its copied text changes.
- Council carry already pins the destination's saved chain through `pinSavedDocument`/`captureCouncilCarry`. Rebase its actual predecessor after ACK; never silently adopt a separately colliding create or make participants wait for their own embedded creation.
- Feature code uses the public engine facade. Do not add a screen retry queue, sort actions by device clocks, serialize all documents, add wire dependencies to an existing operation, or turn a local planned source into a confirmed snapshot.

Regressions: `app/data-engine/__tests__/linkedCreateDependencies.test.ts` and `linkedCreateRecovery.test.ts`; the existing pending-destination carry control is in `councilCarryAtomic.test.ts`.

## A later deletion must follow already saved uses

`data-engine/deletionOrdering.ts` owns the inverse order. When a DELETE is first captured, the native request store scans existing owner requests inside that same read/write transaction and freezes `deleteAfter`: active earlier requests using the exact resource, through the canonical document/command reference rules. There is no clock comparison, extra transport queue or wire dependency. The new `ordered-delete-request` capability range keeps older bundles from preparing semantics they do not understand; generic dependency-reference rows retain prerequisite payloads even for older collectors. A repeated capture reuses its original frontier. A legacy row with no frontier stays legacy; later records cannot reconstruct its original order.

`CommitQueue` waits before preparation while any captured prerequisite is not terminal. An unknown delivery remains pending and reuses its original operation. ACK, conflict, refusal and explicit cancellation settle the earlier request; its retained words and normal recovery remain. Unrelated resources continue independently. Do not add `deleteAfter` to the wire, rewrite an existing command fingerprint or treat a missing prerequisite payload as proof of completion. The local frontier does not establish chronology between unobserved actions on different devices.

`relationMirrors.ts` declares only reverse indexes and retired back-references: note `materialIds`, sermon/group `seriesId` and `seriesPosition`. Client preparation and server ordinary-update admission use the same ownership list. DELETE compares authored content while excluding those collection-scoped mirrors and its existing bookkeeping fields. A material save may have added a reverse link while deletion waited; that alone must not block deletion. The cascade still updates the actual owning material/series, while changed words/title and generation/ownership checks retain their protection. Do not expand the exemption to canonical membership arrays or arbitrary derived fields.

Regressions: `sourceDeleteOrdering.test.ts`, `sourceDeleteRelationOrdering.test.ts`, `deletionOrderingStorage.test.ts` and the DELETE controls in `protocol.test.ts`. These cover actual engine/planner ordering and transactional storage-adapter semantics; native responsive acceptance and rollout proof belong to the verification ledger.

## Search the complete atomic relation scope

- `serverRelations.ts` owns semantic selection. The server reader in `server.ts` applies it before the selected-participant quota, reading owner-scoped pages ordered by document ID inside the same Firestore transaction. Continue past pages with no matches; stop only at exhaustion or the requested matching limit (including the planner sentinel).
- Keep `currentItems` legacy fallback for series, root and section-only note membership, typed member identity, and the final staged-series overlay. Existing `sermonIds` or root `noteIds` indexes alone do not cover all historical references.
- The membership selector pins the complete catalog for an immutable opening view, recovery and source discovery. Do not limit this catalog by the command participant quota. `MembershipScope.captures()` includes only changed series and an explicit target/creation; `CommitQueue.saveAtomic`, atomic identity, domain commands and server scope retain their actual participant limits. Cover large restored catalogs and optional creation selectors as well as oversized real effects.
- Preserve overlap plus sentinel and the 100-resource total scope: a simple delete allows 99 related series plus the primary; 100 related refuses with no partial effects. The quota bounds selected participants, not read work: discovery remains O(N) reads and is subject to Firestore transaction deadlines and contention. A complete flat index needs a separate migration before it can replace discovery.
- Regressions: `__tests__/data-engine/server.test.ts` (305 unrelated rows, late matches/duplicates, 99/100 boundary) and `serverRelations.test.ts` (legacy identities, staged moves, ownership and atomic refusal). `app/data-engine/__tests__/membershipScope.test.ts` covers large restored/creation catalogs and real oversized capture refusal. Recipe changes must retain both successful ordinary actions and genuine refusal cases.

## Legacy paths (unconverted collections only)

These compatibility paths are not templates for new features. `frontend/app/services/seriesMembership.client.ts` remains a compatibility writer.

- The legacy membership writer stores transforms (`add` / `remove` / `reorder`). Online: one transaction over every series it touches, reads first, each transform applied to what is stored; a missing target aborts the whole move. Offline, with a signed-in owner, the transforms are queued all-or-nothing in localStorage and `replayMembershipOutbox` replays them one entry at a time through the same transaction. Exception: when that storage refuses, or no one is signed in, it falls back to a Firestore batch of computed arrays (`frontend/app/services/seriesMembership.client.ts`) — that path can overwrite a concurrent membership change, so never copy it as a safe merge. `sermonIds`, `seriesKind` and the `rev.items` counter move in the same write.
- A change that touches two documents (a move between series) lands whole or not at all; never report success for half a link.
- Derived side: `getSeriesForRef(refId, seriesList)` / `buildInSeriesRefIds` over the cached series list; "sermons built on this note" filters the cached `sermonListKey` list by `sourceNoteIds`. A new relation takes the same shape.
- A list-valued link is written through the guarded door (`updateSermon` → `conflictSafeUpdate`) with the revision the editor rendered and a baseline of exactly that one field, captured at open time (`openingContextOf`). Keep `null` (never linked) apart from `[]` (emptied): the guard hashes a missing field as `null`, so an opening `[]` on a never-linked sermon would refuse every first link. Test the list with `Array.isArray`, not truthiness — a writer that skips falsy values makes "remove the last link" a no-op (`frontend/app/services/sermons.client.ts`).
- Publish the result as a patch each owner of a copy merges (`applySourceNoteLinkPatch`), never a whole entity.
- Do not write a no-op: compare with what is stored first (`sameIdSet`). Linkage is index metadata — a membership write touches only series documents, and a sync or repair loop must never rewrite unchanged siblings, or it bumps their `updatedAt` and they look freshly edited.

### When a legacy link goes wrong

- Badge says "series", series page is empty → compare the series document's `items` with its `sermonIds` mirror (`seriesContainsRef` reads both); a sermon's `seriesId` is not evidence. Repair through the membership writer, which rebuilds `items`, `sermonIds` and `seriesKind` together.
- Suites that render a parent break after adding a child that uses React Query → stub the child there as the file already stubs `OptionMenu`, and let the stub echo its props so the wiring stays asserted (`MockSourceNoteChips` in `frontend/__tests__/components/sermon/SermonHeader.test.tsx`).
- A count label shows English in Russian or Ukrainian → add `_few` and `_many` beside `_one` / `_other`.

## Why

- 2026-02-25 / 2026-05-01: `entity.seriesId` and `series.items` were two stores; writing one without the other produced "badge says series, series says empty". Since then `series.items` is the single truth.
- 2026-03-19 / 2026-04-25: unconditional sync writes rewrote unchanged sibling sermons and made them look recently edited.
- 2026-08-16: the note ↔ sermon link already had two dead half-implementations when it was built live; storing only `sourceNoteIds` avoided a third mirrored copy.
