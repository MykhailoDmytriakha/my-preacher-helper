# Run a demo on the Firestore emulator

A demo, or a live check that needs particular data, runs against the local Firestore emulator: the shared production database is untouched (no load, no test data among real records) and the demo still works when production refuses reads. The dev test user signs in for real; only Firestore is local.

## How

- **Emulator.** A folder with its own `firebase.json` (`firestore` on a free port, `hub`/`logging` ports shifted, `singleProjectMode`), a copy of `frontend/firestore.rules` made at every start (the emulator refuses rules outside its folder), `--project my-preacher-helper`, `--import` from a preserved data folder so the demo survives a restart. Use `--export-on-exit` only for a single isolated suite; concurrent suites and restart acceptance checks must use the explicit owned-hub export described below. The firebase CLI is `frontend/node_modules/.bin/firebase`. Real ID tokens are accepted (the emulator warns it does not check signatures).
- **Server.** A second `next dev` on its own port with: `NEXT_TYPEGEN_DIST_DIR=.next-<name>` · `NEXT_PUBLIC_FIRESTORE_EMULATOR=true` and `NEXT_PUBLIC_FIRESTORE_EMULATOR_PORT=<port>` (browser SDK, `app/config/firebaseClientDb.ts`) · `FIRESTORE_EMULATOR_HOST=127.0.0.1:<port>` (Admin SDK in routes) · the engine switches from `.howto/fix-stuck-dev-server.md`.
- **Data.** Write through the app's own path: sign in by REST (`identitytoolkit … accounts:signInWithPassword`, the dev login from `app/utils/testLogin.ts`) and POST `/api/data-engine/commands` with `{ protocol: 1, operationId, owner, resource, generation: null, dependsOn: [], kind: 'create', value }`. A document written straight into the emulator has no `_dataEngine` metadata and no change-feed entry. The `users/{uid}` profile is created by the app at first sign-in.
- **Looking at it.** Drive a headless Chrome (Playwright, `channel: 'chrome'`, a persistent profile per viewport, cookie `lang=ru`). Screenshots from it are the visual evidence.
- For autonomous multi-service QA, run the full start/scenario/export/stop cycle under a separate bounded supervisor. Persist each owned process identity and temporary profile before waiting for it; a model/tool timeout must not leave data views or servers running. Keep service child logs and wrapper logs distinct. Propagate the actual scenario/worker failure even when cleanup succeeds.
- A Node worker must await its stand-stop child asynchronously. Blocking that worker with `spawnSync` prevents it from reaping exited service-wrapper children; `kill -0` can then report a zombie even though the recorded child exit was0 and all ports are free. Preserve that failed cleanup command, audit actual PIDs/exports separately, and use async spawn + bounded timer + actual close on the next run. Unit279 HL and HL2 retain this distinction.
- Worked example with every script (start, seed, walk scenarios, stop): case `2026-10-19-mesto-pisaniya-tekst-i-gde-esche-ispolzuetsya`, folder `demo/`.

## Why

- 2026-10-19: production answered `RESOURCE_EXHAUSTED` to every read while the owner asked for a demo with full data; seeding production was impossible and would have mixed test records into the shared base. The emulator stand showed the feature the same day.


## Observe the recovery state before choosing a button

An emulator outage does not imply every warm tab has received a failed request. For a cached-profile control, check the preserved profile and absence of a separate settings failure; require the global outage line only after establishing an actual failed browser read in that context.

After restarting the owned emulator and application, a collection can recover on its ordinary observer before a planned Retry click. If the button is gone, verify the actual successful browser collection response, cleared global line and truthful current list state. Click Retry only while it is still offered. A profile whose opening failed may still need its own Settings Retry; verify that actual button and successful profile read separately. Keep automatic recovery and a clicked retry as different evidence claims.

A native scenario must use the screen's actual panel: council detail has its own `council.readFailed` panel; it does not use the generic `data-record-unavailable` selector. Preserve failed scenario reports and correct the predicate instead of calling an unmet test assumption a product defect. Evidence: `settings-outage-131-native-v{1,2,3}-adjudication-v1.json`.


## Hold an actual read instead of assuming one

A warm Back or initial list-backed marks opening need not issue a document GET. Require an actual intercepted request before judging a pending-read scenario. Capture the real local response, hold only its delivery, and record native hidden/visible timestamps plus the request's cancellation event. The8s CRUD network timeout can fire before the10s outer owner-request deadline: crossing a guessed deadline does not prove the failure happened while hidden. Unit171 keeps the excluded no-interception and wrong-time-window probes beside the accepted native cases. A clean replay preserves the owner-reported bug; it is not a fix or administrative closure.

For manual sermon fields, distinguish a cold document read from an editor opening over its cached snapshot. A cached reload can open without another document GET, so a barrier waiting for that request measures an unmet harness assumption. Record the actual request before releasing a cold-read barrier; probe ordinary cached reloads without that barrier. Observe the public DOM and use a trusted real pointer event when the pencil becomes enabled. Retain the time between that observation and the event: this is bounded early-click coverage, not proof that every React effect interval or physical slow device was exercised. Unit264 keeps the excluded cached-GET timeout next to four qualified title/verse cases with 36 early clicks.
