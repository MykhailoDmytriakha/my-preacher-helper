# Set up and run the service worker

The service worker is built by Serwist (the successor to next-pwa) from `frontend/app/sw.ts` into `public/sw.js`, configured in `frontend/next.config.mjs`. Production always has it. In `next dev` it is on only with `NEXT_PUBLIC_ENABLE_SERVICE_WORKER=true`, which `npm run dev` and `npm run dev:pwa` set and `npm run dev:no-pwa` does not. For true offline parity use `npm run preview:pwa` (`next build && next start`).

## How

- Add a route rule to `runtimeCaching` in `frontend/app/sw.ts`, BEFORE `...defaultCache`. Serwist's `defaultCache` sends same-origin `GET /api/*` through `NetworkFirst` (cache `apis`, network timeout 10 s): a GET slower than 10 s is answered from the cache.
- A slow AI generation exposed as a same-URL `GET` must bypass that cache: a `NetworkOnly` rule (as for `/api/sermons/<id>` and `/api/sermons/<id>/plan`), `Cache-Control: no-store` on the response (`jsonNoStore` in the plan route), a unique request id, or a non-GET method (`defaultCache` caches `GET` only). Otherwise a slow model answer is replaced by an older cached one.
- Firestore never enters Serwist: the `fetch` listener returns early for `firestore.googleapis.com`, and the Firestore SDK owns offline data.
- Offline data does not depend on the service-worker switch: Firestore `persistentLocalCache` (`frontend/app/config/firebaseClientDb.ts`) and the persisted React Query cache stay on in every mode. Keep it that way; turning the worker off must not turn offline data off.
- An offline navigation whose HTML was never cached gets the precached `/~offline` shell (`frontend/app/~offline/page.tsx`, `additionalPrecacheEntries`, revisioned by `VERCEL_GIT_COMMIT_SHA`). `reloadOnOnline: false`: a reload on reconnect would wipe unsaved form state.
- The explicit shell precache also owns `/manifest.webmanifest` and the six linked browser/Apple/PWA icon files (`next.config.mjs`, `appIconSources`). Static icons use SHA-256 content revisions; the generated manifest uses the existing shell build revision. Keep this list bounded: omitting `additionalPrecacheEntries` makes the installed Serwist integration scan all of `public`, including Bible/audio resources. Update the linked-resource regression in `__tests__/serviceWorkerPrecache.test.ts` when metadata changes. Test a cold worker before any explicit icon fetch, then hard offline and reload; successful online responses alone do not prove offline availability.
- The shell renders its pages inside `PrivateWorkspace` and `PrivateChrome` (`frontend/app/components/PrivateWorkspace.tsx`), the same two components the private layout uses: the data engine, the settings, the banners and the queue workers reach a page the same way online and in the shell. A provider added to only one of the two leaves the shell's pages without it — that is how the shell once showed every engine list empty.
- In `next dev` Serwist builds the worker with no precache manifest and no additional entries, so `/~offline` is not precached there. Test the offline shell with `npm run preview:pwa`.
- A live check of the shell on a production build: build with the production engine switches (`docs/architecture/data-engine-migration-log.md`) and `NEXT_PUBLIC_ENABLE_TEST_LOGIN=true` (the test-login button is otherwise dev-only), open the page online, delete its document from Cache Storage (`pages`, `others`, `pages-rsc-offline`), stop the server and open the address again. The automation tab reports itself hidden and the engine reads nothing from the server while hidden — make it report visible first (`.howto/read-owner-documents.md`).
- An offline client-side navigation is answered by `frontend/app/utils/offlineRscNavigation.ts`: for every address the person has seen online the worker keeps the RSC payload rendered against the `/~offline` shell's tree, which patches right under the root and so fits whatever page is open. "Seen" is told by the page (`frontend/app/components/OfflinePageMemory.tsx`, posted on every committed address and again on `controllerchange`), not guessed from traffic: a navigation served from Next's prefetch sends no request, and the first page loads before the worker controls it. Never key real navigation payloads without `_rsc`: a payload diffed against another page may not fit, and Next then changes only the URL and keeps the old screen.

- A weak signal — a request that neither answers nor fails — is answered by `answerWithinDeadline` (`frontend/app/utils/offlineRscNavigation.ts`); reuse it, do not write a second race. With a copy on the device the network has 3 s from the navigation to arrive whole, then the copy answers and the late answer is cancelled; with nothing kept the network passes untouched. What the copy may replace is the caller's call (`replaceable`): an RSC navigation passes `isFlightPayload`, supported shell documents (`sw.ts`) pass nothing. Only copies that cannot be out of step with the build get a deadline: the precached `/~offline` shell and the kept RSC payloads. The deadline also covers same-origin documents recognized by `utils/offlineShellRoutes.ts`, the single route catalog consumed by the worker and shell. Settings addresses still derive from canonical `settingsSections.ts`; its section type requires a lazy component when a section is added. Unsupported, public/auth and API addresses keep their existing handling. The shell shows a neutral pending card while lazy code is loading and lets that code finish; a pending import must never be represented by `Suspense fallback={null}`. It uses the existing same-build precache rather than storing another HTML copy.

## Keep required application code from the first activation

`scripts/pwa-precache.mjs` owns the bounded 4 MiB per-file precache policy and `requireAppCodePrecache`, wired into Serwist through `next.config.mjs`. It verifies actual emitted production `static/chunks/*.js` and `static/css/*.css` against the manifest after size filtering. Missing application code fails the build; split the chunk or deliberately revise its budget instead of accepting an offline failure. Source maps, hot updates, worker outputs and unrelated media are outside this code contract. The additional public resource list stays explicitly bounded; Bible text/audio and private API replies retain their existing owners.

A first visible page can load before worker control. Runtime interception then misses its original code requests, so a later controller and cached shell do not establish that the page can reload offline. Check the real generated manifest and actual CacheStorage before the first offline document reload, without an extra online reload or manual cache write. A normal online reload is a separate useful control. Keep lazy route imports: precaching emitted code does not require adding every page to the shell bootstrap.

`serviceWorkerPrecache.test.ts` resolves actual config and runs the public Serwist transformer with size metadata: ordinary and 2.5 MiB code are retained, missing or over-budget app code fails, and optional large media remains bounded. A real production build and fresh-browser first-view reload are still required. The original defect excluded an unchanged 2,368,021-byte shared Bible/Studies chunk under Serwist's [default 2 MiB limit](https://serwist.pages.dev/docs/build/configuring/maximum-file-size-to-cache-in-bytes).

## Traps

- Next applies an RSC answer only when its content type starts with `text/x-component`, case-sensitive; anything else it opens as a document. A worker that substitutes a kept payload for such an answer hides that decision — ask Next's check, never compare the answer with the copy (2026-10-12: comparing types let a start page without a content type bypass the shell, and `TEXT/X-COMPONENT` hid a document navigation).

- Localhost fails intermittently on first load after switching to `dev:no-pwa` → a worker from an earlier run still controls the origin, and `public/sw.js` is still on disk (a disabled Serwist neither unregisters nor deletes it). Unregister it (DevTools → Application → Service workers) and name the mode explicitly in the command you run.
- `GenerateSW has been called multiple times` was next-pwa regenerating the worker in webpack watch mode. Serwist builds with the precache manifest disabled in dev and returns before its own `InjectManifest has been called multiple times` check, so under `next dev` that warning is not expected.
- After a deploy an open tab keeps running its loaded bundle until a real reload (`skipWaiting` and `clientsClaim` swap the worker, not the code in memory). `AppUpdateButton` offers the reload once `/api/health` reports a different version.
- Checking offline behaviour on a local production build gives false results after a rebuild: the shell's precache revision is `"dev"` (`next.config.mjs`, no `VERCEL_GIT_COMMIT_SHA`), so the worker keeps the shell of an older build, and Next rejects every payload of the new build by its build id. Unregister the worker and clear Cache Storage before each such check.

## Why

- 2026-10-12: on a weak signal the installed app's start waited 20–30 s and more (BUG-20261004-weak-network-delays-offline-navigation): `NetworkFirst` had no time limit, and the kept RSC payload was read only after a request failed.
- 2026-09-30: every tap without network reloaded the whole app (BUG-20260927-offline-navigation-reloads-whole-app): `_rsc` hashes the page being left, so a full-URL cache missed almost always.
- 2026-05-24: an AI generation `GET` slower than the worker's network timeout was answered from the `apis` cache.
- 2026-05-10: an old worker still controlling localhost while the dev run had the worker off made first-load failures intermittent and misleading.

## Verify bounded documents and pending code

Use a fresh disposable browser context against a compiled production build and verify its actual controller and precached `/~offline` build ID. Warm a supported page, then hold the exact current HTML request without breaking assets/API; `/settings` redirects to a section such as `/settings/user`, so assert `page.url()` before holding or reloading. A new document and its saved body must appear around3s while the server response is still held. Release and reload normally too. A new tab/direct address is a separate case; do not count the previous document still visible during a stalled reload as success.

To exercise missing code, retain the shell's bootstrap scripts, delete other JS CacheStorage entries only in the disposable context, and hold JS requests at an own reverse proxy. Verify an actual held chunk, neutral waiting/Home/Retry, then release and observe the page without clicking Retry. Also check hard offline/reconnect and narrow/wide originals. Private API replies remain synthetic/read-only in this stand; this proves real worker/browser routing, not production data, provider or physical-device acceptance.

Playwright `serviceWorkers:'block'` replaces `navigator.serviceWorker.register` with an async function returning undefined (installed coreBundle.js), unlike normal browser registration; Serwist then reads `registration.waiting` on undefined. This is an invalid no-worker product control. For an explicitly simulated unsupported-API control, remove the serviceWorker property in an init script and assert no controller; normal HTML must continue waiting until the held server responds. Do not label that control a physical-browser setting test.
