# Use the data engine in a screen

A screen on an engine collection reads and edits only through `frontend/app/data-engine/react.client.tsx`: `useDataDocument` for an autosaving document, `useDataForm` for a Save-button form, `useDataCollection` for a list. Transport, revisions, outbox, conflicts and recovery belong to the engine; the full contract is `frontend/app/data-engine/README.md`.

## How

- One editor per document per page: wrap the page in `DataDocumentProvider`; matching `useDataDocument` / `useDataForm` calls inside share it. Each opening gets a fresh editor identity; old work comes back only by explicit recovery (`useRecoveryDiscovery`, then `recover(id)`).
- One editor, one voice: since the hooks share the editor, their `status` / `error` and resolve actions describe the same delivery, so the page shows ONE `DataSyncStatus` with them — the one always on screen (the sermon page: the header). Other blocks on that document pass `status={null} error={null}` and keep only their own recovery list; two blocks asked a conflict twice (BUG-20261006-sermon-conflict-choice-shown-twice, `EngineScratchWorkspace.tsx`).
- Lists render `documents` from `useDataCollection` with `DataCollectionStatus`: submitted local work included, flags `pending` / `needsAttention` / `deleting`, a pending deletion addressable until ACK. They are presentation built by the editors' `DataSession` rule (`frontend/app/data-engine/collectionView.ts`) — never seed an editor baseline from them or any list projection.
- A whole-document create form keeps the public `useDocumentActions().create` promise intact and awaits `awaitWriteOperation` (`utils/recoverableWrite.ts`). That promise proves durable local capture only; the helper returns no server-delivery receipt. Never place a timer-based `queuedMutation` wrapper around it. A failed capture keeps every field and has one local reporter; after capture the existing engine notice owns server refusal. Examples: `usePlanTemplates`, `useTags.addCustomTag`, `usePrayerRequestsEngine.createPrayer`; the dashboard waits on the same prayer capture before navigating to its attached stable ID. Keep repeat submissions blocked and preserve text typed for the next create while the first waits. Legacy WriteSubmission remains supported for its own writers.
- One document edited many times in quick succession (strokes, taps, picks) is a FORM's job, not a row of one-shot actions: open one `useDataDocument` for it and `commit(updater)` each change at once — the form lays each change on its newest draft, keeps it on the device before the network is asked, and chains the requests (since 2026-10-16 the predecessor is chosen when the save runs, `controller.ts` ~164; before, saves captured while the first was pending all branched from it and the server answered `conflict`). Separate `useDocumentActions().commit` calls each open a new editor on the same copy and conflict with each other (Bible marks on the owner's iPad, 2026-10-16); serializing them by hand leaves the waiting changes in page memory during a delivery. Example: `components/bible/marks/markStore.ts`. Class, 2026-10-16: service orders serialize one-shots per id (`useServiceOrdersEngine.ts` `queued`); prayers' quick writes touch different fields or id-keyed lists; tags — the same field changed twice in a blink could still collide, not checked live.
- A document under a FIXED id that another device may already have made (one per person and book, as `bibleMarks`): never pick `create` because a list lacks it — the list may not be read yet, and a create over an existing id is refused `already-exists`. Use `useDocumentActions().commit(resource, current => current ? change(current) : fresh())`: the editor reads the document itself (this device's copy, else the server) and creates only where it is absent. Offline with no copy the read refuses `needsConnectionFailure(error)` (declared in `react.client` — a re-export of an engine function is caught by `__tests__/architecture/dataEngineBoundary.test.ts`); only then, and only if the read list lacks the document, fall back to `create` — a collision is then a refusal the engine asks the person about. Gate the screen's tools on `!collection.loading`. Example: `frontend/app/components/bible/marks/markStore.ts` (2026-10-16).
- A direct page-hide Save can follow an adopted manual Save at the same parent generation. Include that generation when choosing a predecessor. If both manual and parent captures share it, use their durable dependency chain, not array order or the number alone: controller passes the newest eligible candidate IDs to the existing CommitQueue, which selects the descendant and refuses unrelated candidates without an extra store read. Later captured generations stay excluded. Regression: engine.test.ts manual page-hide and richer parent title cases (BUG-20261016-manual-save-parent-branches-on-hide).
- After navigation or restart the engine continues one unambiguous submitted chain in the new editor, keeping each request's identity (`frontend/app/data-engine/submittedWork.ts`). Unsent typing and competing branches stay explicit recovery choices.
- A fresh unpublished opening can race with acceptance collecting its loaded request. `DataEngine.open` retries only `commit-reference-changed`, at most twice after the first attempt, through the existing failed-entry cleanup and the same editor identity. It requires the original owner/generation and an un-aborted signal. Reread durable state; never weaken reference validation, recreate an accepted request or retry ordinary disk errors. This does not retry an active editor or a manual form pinned to already displayed fields.
- Save-button form = `useDataForm(resource, slot, selection)` in the same provider: `begin()` pins the opening ancestor of the selected fields, `update()` stages durably unsent, `save()` submits, `cancel()` retires only unsaved typing. Never apply component-local text to the newest document at Save. Examples: `CouncilOutcomeForm`; `EngineEditSermonModal` (metadata + dates); `EngineOutlineModal` (outline + dependent thoughts and placement; `OutlineBoard` `directText` stages each keystroke, one outer Save submits).
- Show the form's own `status` / `error`; resolve with its `keepLocal` / `acceptRemote`. A clean form keeps the document's queued / conflict / refused status. Keep local may carry corrections staged after a known failed Save, suspended on disk until the replacement request is durable; resolution refuses while unsent input exists in or outside the form's fields.
- Slot + selection name the action; discovery and direct recovery both match resource, slot and selection, so opposite actions over the same fields never exchange drafts. `EnginePreachDateModal` uses one slot per action kind over `preachDates` + `isPreached` (pure transforms in `frontend/app/components/calendar/preachDateForm.ts`); `PreachDateModal` requires `sermonId` and routes there, the dashboard menu skips legacy optimistic writers (Legacy path; removed 2026-10-13 — `PreachDateModal` and the legacy optimistic writers are gone, `EnginePreachDateModal` is the only one), history (`EnginePreachDateList`) reads the shared document. A recovered mark follows the changed row's durable ID, never a nearest date or the clock; unmark touches only opening rows and keeps remotely added dates. Read status with `getEffectiveIsPreached`, not the legacy flag.
- An acknowledged or cancelled Save is terminal for reopening and compaction; a cancelled one is never adopted as the value.
- A conflict choice retires saved intent in two stages: `CommitQueue.cancel` / `cancelAction` first persist `cancelled` plus `unfinalized`, retaining the terminal receipt if that transaction fails. The deciding owner applies and durably persists its chosen editor/action projection, then calls targeted `finishCancellation`; do not substitute a global delivery drain. A cleanup error after this point cannot replace kept words with the remote copy. Retry/restart can finish only cleanup, without sending decided intent again.
  - Cover every owner: controller `acceptRemote` / `keepLocal`, membership discard, council discard, and the global `takeStoredVersion` notice after leaving a screen. Mounted projections settle before action/global cleanup; ordinary choices persist their checkpoint first.
  - `commitJournal` owns cleanup classification. A request-level conflict may follow an acknowledged relation plus an ordinary-field rebase conflict; inspect the actual journal receipt and finalize the acknowledged operation. Only a terminal refused/conflict command is discarded. Unknown outcomes remain protected by runtime guards.
  - Cleanup CAS can race with the existing worker. Re-read on bounded `commit-changed`; already-cleared ownership is successful retirement. Nonempty `unfinalized` protects ordinary/atomic records from compaction until cleanup is durable.

- A read screen with `autoSave:false` that offers document Keep local must explicitly `await keepLocal(); await save()` in its choice handler. The document API deliberately keeps the resolved result as a draft; without the Save it becomes an orphaned selected-field draft on a screen with no Save button. Both series detail/status surfaces share `saveKeptSeries` in `EngineSeriesDetail.tsx`. Keep ordinary manual typing stage-only; `useDataForm.resolve` already submits its selected choice and needs no extra Save. A failed keep/cancellation must stop before the replacement Save; offline that Save stays durable and queued.

- A null draft over an existing record is a local deletion, not text to keep. `describeSync` derives `deleting`; `DataSyncStatus` offers existing Keep record / Delete anyway (or Retry delete) words. Keeping the record accepts the stored version without a text-discard question; repeating removal uses the shared delete confirmation and retires it if subject/deletion availability changes. `describeManualSync` clears this whole-record intent for every selected-field form, including inactive/opening fallbacks. Never label a deletion as Keep my text.

- A global recovery choice owns the copies it showed, even if another local save arrives after its final read. `captureRecoveryChoice` keeps the existing record fingerprint and operation IDs; pass that confirmed target through `EngineConflictBanner` into settlement. `takeStoredVersion(resource, ids)` selects only those answered request roots and uses canonical `cancel('', ids)` / `finishCancellation`, so dependent cancellation and later ordinary typing retain their existing projection. Empty IDs cancel nothing. A fresh resource-wide read must never expand the explicit choice. Scoped one-shot discard uses the same request projection; do not reopen and clear modern checkpoints afterwards. Legacy direct commands still require the exact shown checkpoint, checked inside the controller queue.
- A directly owned legacy command has exactly one pending ID and the matching persisted `prepared` command (`documentDelivery.isDirectLegacyDocumentIntent`). It never had a modern CommitRequest. Both controller choices retire it through the runtime's terminal-command guard, without requiring an empty modern queue to prove a choice. An absent modern request, mixed pending work or unknown delivery does not become legacy: retain the strict queue/runtime refusal and the person's words.

- Conflict buttons use the complete saved intent, not just a command receipt. A relation ACK can leave an ordinary-field rebase conflict in the same request. The managed editor derives `savedIntentReplaceable` through `documentDelivery` and the queue's existing `cancellationScope` / `canCancelSavedIntent`: every held request must exist, unknown siblings block, and atomic scopes stay whole-action choices. A real conflict candidate is selectable even when its metadata names our relation ACK; an ordinary own SDK echo stays silent. Directly owned legacy `checkpoint.prepared` commands retain their terminal-journal calculation only when that is the single held operation. Missing modern request records never get that exception.

- AI output: `form.propose(async source => next)` gets a durable frozen source; output after another edit, cancel, owner change or close is rejected; accepted output only stages. `EngineOutlineModal` with `withScratch`: `scratchComposeSource` binds the AI inputs; Apply submits outline, thought links and scratch consumption as one action, and `scratchConsumptionConflicts` (`frontend/app/data-engine/sermonIntegrity.ts`) checks consumed notes in the same server transaction — a changed or deleted source conflicts the whole action. Close and restart keep it unsent; conflicts use the same Keep local / Accept remote.
- Text controls over an engine draft use `useBufferedText` (`frontend/app/components/ui/useBufferedText.ts`): it protects only keystrokes not yet echoed; focus never gives a field its own baseline. TipTap programmatic replacement passes `emitUpdate: false`.

## When it goes wrong

- Save after reopening is lost → an editor identity was reused → fresh identity per opening, shared through the provider.
- Recovery offers requests already delivered → mounted editors and recovery must project ACKs by the same `DataSession.applyCommit` rule before listing.
- Closing a form leaves an error in the next editor → retirement rejects queued work with `InactiveEditorError`, and `DataEngine.background` suppresses only that type. Never silence every failure of a closed editor: a real `Disk full` after close must still reach the facade's error.
- The server refuses a save after its screen closed → nothing is lost: the request waits in the journal, and any editor opened on that document again inherits it. It shows the refusal through `DataSyncStatus` with three choices: keep mine, use the server's version, and retry. Use the server's version drops the refused change: `EditorController.acceptRemote` runs `DataSession.dropRefused` as a three-way merge from the draft at the moment of choice, so a field typed after the click stays. For a conflict the choices are keep mine and take stored.
  - The decider's cancel marks what it held as `cancelledByChoice`. Any other editor that held that work (closed, or still open in another tab) settles in `DataSession.applyCommit`, which is one rule for mounted editors and for recovery's projection. If its latest request was decided and its draft is exactly that request, it takes the decider's version. Work swept along as a dependent only loses its now-stale conflict and stays a recoverable draft.
  - A form's work (a request whose `editorId` is no editor identity, so `editorSlot` returns null) stays with the form, as before. The editor marks it (`manualWork`), the screen offers no refusal drop for it, the banner leaves the document alone (`formWorkPending`), and `takeStoredVersion` cancels nothing.
  - Recovery words and copied text exclude generated recording receipt fields (`dictationSourceIds`, `recordingSourceIds`) through the banner's existing BOOKKEEPING rule. Keep those IDs in the exact saved draft, request, fingerprint and source-ownership checks. Do not translate raw IDs into prose, hide unknown authored fields, or change archive equality to improve this presentation. Mounted recording regressions cover conflict/refusal and one-shot/screen notices.
  - `EngineConflictBanner` decides one-shot drafts itself (`isOneShotRecord`, slot `action`, reserved). For a screen's answered draft it shows the words (a list of items as the words of the items that changed, never ids or positions) with a link to the screen (`documentScreenHref`) for keeping them, and offers the server's version right there (`takeStoredVersion`): a notice on every page with nothing to decide in it is what the owner could not get rid of (BUG-20261013-screen-draft-notice-offers-no-choice). The exact held-work and route checks below decide when the answering screen owns that question. If several chains mean no screen can take the work over (`screenDecides` is false), it shows every draft for copying and offers the server's version (`takeStoredVersion`), which reopens no editor.
  - The notice observes `useOpenDocumentAnswerScopes`: the open answering editors' owner, resource, held request IDs and draft. Through the public facade, `isRecoveryHeldOpen` yields a whole waiting group only when every saved record has nonempty pending IDs covered by an answering editor with the same words. This applies to adopted one-shot work too; the reserved `action` slot has no answering screen. Keep the route check: a matching URL without an answering editor cannot hide the only notice. Independent requests or later words in the same request stay globally discoverable. Do not filter individual records out of a group: the choice resolver still owns that complete group. The same selector must run before rendering and both confirmation-time rechecks (BUG-20261016-one-shot-answer-notice-doubles-on-document).
  - Every branch of an answering screen must actually render its existing status. A null draft can be an answered deletion, not just a missing record (sermon missing branch). A document may already hold the answer while a separate form is still opening (group meeting-loading branch). Keep the status/feedback visible in those branches; do not weaken the exact-work matcher or hide the person's only decision.
  - Opening/closing or changing held words republishes the exact answering snapshot immediately, without a journal update or recovery-poll delay. The older `useOpenDocumentAnswers` resource view remains compatible and publishes only a changed resource set, not every keystroke. On owner retirement detach the entire editor registry before invalidating controllers, so publication never inspects another retired controller mid-close.
  - Until the person decides, one-shot actions answer `decision-required`. Do not exclude screen drafts from that gate: a one-shot editor opens on the local head, which still carries the refused text (BUG-20260813-late-refusal-silent-after-navigation; five Codex rounds, 2026-10-03).

- The breadcrumbs (or other chrome around a page) keep an old name after a rename → they read the legacy React Query cache, which engine writes never update. Do not give the chrome its own reader: a collection reader opens the whole collection for one word (review counted ~650 reads/hour for 50 sermons while the legacy road is open) and can lag the open document. The hook that already holds the document publishes its title with `usePublishShellTitle` (`components/navigation/shellTitles.tsx`), and the chrome reads `useShellTitle` (BUG-20261004-breadcrumb-keeps-old-sermon-title).

## Seed a standard service-order catalog

Use the same public create capture; shared utils/serviceOrderSeedIdentity.ts owns owner/catalog/cycle identity. Choose the next target only from a complete server-fresh collection including tombstones; live presentation rows alone cannot prove the next identity. A new explicit seed after deletion names a new resource, while an old delayed action keeps its deleted target. The standard namespace cannot hold a mismatched/custom catalog value.

The engine domain policy prepares service-order-seed for canonical standard targets. Its server transaction checks owner/catalogKey uniqueness for both that relation and older generic standard creates. A same-target repeat ACKs the complete stored document with only metadata advancing; authored steps, text, rank and recency remain. Different live targets refuse without merging/deleting them. Reuse the outbox and receipts; do not add a feature queue or writer. Same-window overlapping seed calls coalesce. Cache-only/incomplete refresh says the server must be reached and captures no create.

Seed identities must stay unchanged through existing detail routes: use only URL-safe ASCII. The shared utility encodes owner UTF16 units as fixed-width hex, followed by catalog key and canonical decimal cycle; do not scatter encoders/decoders in screens. Normalize only the pre-seed refresh rejection to OFFLINE_SEED; creation failures must retain their own error. The safe-integer cycle guard deliberately refuses exhaustion rather than wrapping into a deleted target.

- A saved change disappears from the app-wide notice after a relation ACK, or a locally refused request permits more one-shot edits: use the engine's derived `RecoveryCheckpoint.answer`, not only failed command-journal IDs. `documentDelivery.savedDocumentAnswer` reads held request identities with owner/resource checks; modern request state owns the answer, legacy direct commands retain journal compatibility. `listRecoverable`, `getOpenAnswers` and one-shot decision discovery share this knowledge. The field is a query result and is never written to a checkpoint. A transport ACK alone is not a complete request answer; unsubmitted screen conflicts are not global notices. Regression: EngineConflictBanner and engineOpenAnswers use relationRebaseHarness with actual durable adapters and relation policy.

- A first global version choice is rejected until the notice polls: the recovery view depends on both the command journal and durable request answers. Subscribe through `DataEngine.subscribeSavedWork`, which combines the existing journal and CommitQueue events; whole-action membership uses the same subscription. Keep `subscribePending` journal-only, without advancing its hydration version for a request event. Keep owner/disposal fences, exact reviewed-copy guards and the visible-page IndexedDB fallback for other tabs. Mounted regression: EngineConflictBanner holds the conflict request write until its journal notice appears, releases it, then each first choice works with a sixty-second polling interval.
