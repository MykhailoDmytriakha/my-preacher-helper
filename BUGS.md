### Защищённая запись ЛОМАЛА офлайн-сохранение — P0, было хуже HEAD — ИСПРАВЛЕНО (2026-07-25)
**Был.** `conflictSafeUpdate` всегда шёл через `runTransaction`. По документации Firebase транзакции ОФЛАЙН НЕ РАБОТАЮТ — обычные записи ставятся в очередь и доигрываются при реконнекте, транзакции просто падают (https://firebase.google.com/docs/firestore/manage-data/enable-offline). До защиты офлайн-правка заметки/проповеди/серии сохранялась при возврате связи; после — падала.
**Эффект.** Механизм, созданный чтобы НЕ терять текст, сам терял офлайн-правку. Классическое «хуже HEAD».
**Фикс.** `frontend/app/services/conflictSafeUpdate.client.ts`: недостижимость сервера (`unavailable` / `deadline-exceeded` / «client is offline») → деградация ровно в до-защитное поведение — обычная очередная запись с `increment(1)`, не `await` (офлайн `updateDoc` не резолвится). Отказ (`StaleWriteError`) и любая настоящая ошибка НИКОГДА не проглатываются. Возвращается `expectedRevision+1` — безопасная сторона: если кто-то всё же записал, следующее сохранение получит ОТКАЗ, а не затрёт.
**Тесты.** 4 теста в `conflictSafeUpdate.client.test.ts`; мутация «убрать запасной путь» роняет 1, мутация «глотать и отказ тоже» роняет 5. Плюс `useGroupDetail.offline.test.tsx` теперь честно моделирует падение транзакции офлайн и доказывает путь насквозь.

### B9 · TOCTOU перебора usage-лимита при конкурентном burst — P1
**Суть.** Проверка лимита и его инкремент — РАЗНЫЕ шаги. `assertAiUsageAvailable` читает-проверяет ДО провайдер-вызова, `consumeUsage` инкрементит ПОСЛЕ отдельной транзакцией, БЕЗ ре-проверки (`usageLimits.server.ts:105`, `:120` слепой `current+amount`). Два одновременных запроса на 99/100 оба проходят check → оба исполняются → usage уходит за квоту.
**Масштаб — СИСТЕМНЫЙ, 5 потребителей одного примитива:** `structuredOutput.ts:280`, `audio/generate:380`, `studies/transcribe:145`, `thoughts/route:233`, `thoughts/transcribe:144`.
**РЕАЛЬНЫЙ ИМПАКТ (оценка 2026-07-14).** Бьёт только при ИСТИННОЙ одновременности (окно check→increment = мс). Последовательные вызовы считаются корректно (каждый перепроверяет). Обычный UI-юзер: перерасход ~0; две вкладки/двойной клик → 1-2; целенаправленный параллельный burst → больше, но каждый жжёт реальный вызов провайдера и **самоограничивается** (после лимита всё блокируется). Малая база + щедрые квоты (100–5000) → **P1 по классу, но НЕ срочно**; чинить при работе над примитивом, не пожар.
**РЕФРЕЙМ (владелец 2026-07-14): грация, не жёсткий блок → фича.** Владелец НЕ хочет атомарного блока ровно на лимите. Пример: транскрибация = 2 списания (STT+полировка) → одно действие на 99 даёт 101, и это ОК «по благодати». Нужно: (1) действие ДОигрывается (не падает на полпути), (2) мягкий блок НОВЫХ действий за лимитом, (3) hard-cap на бо́льшем пороге (напр. limit+10%), (4) в настройках/админке при перерасходе — тёплое сообщение + СТИХ про благодать. ⇒ B9 из «гонки на устранение» → в **grace-band фичу** (`FEATURE_CONCEPTS.md` F7). Атомарность перестаёт быть критичной (малый overshoot — by design); остаётся hard-cap + сообщение.
**Фикс (направление, из Popper-петли):**
- **Дискретный `aiUsed` (+1, известен заранее):** atomic **reserve+refund ДО провайдера** (проверка+инкремент в одной `runTransaction`; бросок → 429 ДО стрима; refund при провале провайдера). ⚠️ простой rethrow НЕ проходит: `callWithStructuredOutput` (17 вызовов через 8 wrappers) глотает исключение в `{success:false}`/`[]`/500 — надо явно мапить `UsageExhaustedError`→429 на границе роута.
- **Seconds-метры (transcription, audio — сумма известна ПОСЛЕ):** assert(оценка) ДО + consume-actual ПОСЛЕ, БЕЗ throw (иначе после успешной генерации 500 → повторная оплата провайдера). Минимальный overshoot при burst допустим (щедрые квоты). Reserve-before НЕ рекомендован (плохо стыкуется с audio per-batch, риск refund-on-crash).

### Durable draft сам удаляет неподтверждённый текст и не изолирует вкладки — P0 (review 2026-07-25)

**Был/Эффект.** Recovered offer остаётся на экране, пока пользователь может продолжать печатать. Новый текст через 250 мс перезаписывает тот же storage key (`useDurableDraft.ts:158-162`), но `discardRecovered()` удаляет не захваченную recovered-версию, а безусловно текущее содержимое key (`:198-202`). Сценарий: открыт draft R → введён новый N → debounce сохранил N → нажато «Отклонить» для R → удалён N. При crash/navigation до следующего flush unconfirmed N остаётся без durable-копии.
**Фикс (направление).** Offer несёт immutable `{key, versionId, value}`; discard удаляет только эту версию compare-and-delete, а текущая редактируемая версия хранится отдельной записью.

### Freshness не блокирует same-field autosave — исходная потеря текста остаётся — P0 (adversarial review 2026-07-25)
**Был/Эффект.** Banner только отображается; note autosave продолжает через 1,5 с вызывать `updateNote` (`studies/[id]/page.tsx:250-279`) даже при `freshness.state === 'stale'`, а Firestore update не проверяет revision (`services/studies.service.ts:143-157`). Две вкладки меняют одно поле: поздний stale `content` перезаписывает более новый `content`; banner может быть виден, но запись не остановлена. Surgical fields спасают только разные поля, не одно поле.
**Фикс (направление).** Revision/CAS на каждом writer этого aggregate; stale write отвергается, local durable version сохраняется и показывается compare/merge. До CAS как минимум ставить autosave на паузу при stale/unknown, не выдавая «saved».

### Freshness сравнивает server с живым cache, а не с тем, что реально показывает editor — P1 (adversarial review 2026-07-25)
**Был/Эффект.** Все страницы строят `known` из live React Query entity (`studies:767-786`, `sermons:273-290`, `series:98-119`, `groups:248-267`, `prayers:47-65`), а hook переписывает `knownRef` на каждом render (`useDocumentFreshness.ts:68-74`). При mount/refetch cache может получить server v2, пока локальный editor, инициализированный один раз v1, остаётся v1; затем snapshot v2 сравнивается с уже обновлённым `knownRef=v2` и объявляется fresh (`:108-115`). Это тот же запрещённый live-cache baseline, который surgical diff уже исправляет отдельно.
**Фикс (направление).** Передавать immutable opened/last-explicitly-applied baseline редактора, keyed by `{uid,docId}`, а не query entity.

### Freshness selectors пропускают большинство изменений документа — P1 (adversarial review 2026-07-25)
**Был/Эффект.** Sermon наблюдает только title/verse/число thoughts (`sermons/[id]/page.tsx:272-294`), series — несколько scalar + число items (`series/[id]/page.tsx:90-126`), group — scalar + числа templates/flow (`groups/[id]/page.tsx:241-273`), prayer — scalar + число updates (`prayers/[id]/page.tsx:46-70`). Изменение текста thought/template/flow/update при том же количестве, а также sermon preparation/outline/plan, group meetingDates, prayer tags/answerText и series item order дают тот же selected JSON: hook ставит `fresh`, хотя экран stale.
**Фикс (направление).** Сравнивать монотонную document revision/updatedAt, увеличиваемую всеми writers, либо полный canonical hash всех отображаемых aggregates; счётчик элементов не является freshness token.

### `unknown` визуально выдаётся за fresh, а cache snapshot сохраняет старый `fresh` — P1 (adversarial review 2026-07-25)
**Был/Эффект.** При cache-only snapshot hook оставляет прежний `fresh` неизменным (`useDocumentFreshness.ts:95-99`); при listener error ставит `unknown` (`:121-127`). Но все пять страниц рендерят banner только для `state === 'stale'` (`studies:922`, `sermons:1416`, `series:309`, `groups:541`, `prayers:209`). Поэтому offline, permission-denied и terminal listener error внешне выглядят ровно как подтверждённая свежесть; после уже полученного fresh cache-only emission даже внутреннее состояние остаётся fresh.
**Фикс (направление).** Любой `fromCache` переводит в visible `unknown`; unknown имеет отдельный persistent UI («свежесть не подтверждена») и возраст последнего server proof. Terminal error требует явного retry/re-subscribe.

### Own write может поднять banner; `markSynced` может скрыть чужую stale-версию — P1 (adversarial review 2026-07-25)
**Был/Эффект.** Hook игнорирует pending snapshot, но server-ack приходит с `hasPendingWrites=false` и сравнивается со старым `knownRef` (`useDocumentFreshness.ts:93-120`). Ни один save path не вызывает freshness `markSynced`; он используется только в refresh handlers. Если ack snapshot опередил React Query/onUpdate, собственная запись становится `stale` и banner залипает. Обратная ошибка: `markSynced(value)` переводит любой текущий stale в fresh независимо от того, совпал ли `value` с `remote`, и не обновляет `knownRef` (`:136-142`), поэтому может скрыть другую remote-версию или немедленно снова поднять ту же.
**Фикс (направление).** Own write несёт operation/write id и acknowledged revision; suppress только точное совпадение. `markSynced` меняет baseline лишь при exact remote match и атомарно обновляет known state.

### Logout/account switch не гарантирует detach freshness listeners — P1 (adversarial review 2026-07-25)
**Был/Эффект.** Hook корректно зависит от переданного `uid` (`useDocumentFreshness.ts:76-85,130-134`), но sermon/series/group/prayer передают owner из cached document (`sermons:284-288`, `series:113-117`, `groups:261-265`, `prayers:59-63`), а не текущий auth uid. При logout/account switch cached entity может остаться прежним, prop не меняется, effect не cleanup'ится; Security Rules позже могут завершить listener, но тогда UI лишь скрыто переходит в unknown. Дополнительно detail query keys sermon/group/series не содержат uid (`useSermon.ts:58-68`, `useGroupDetail.ts:41-52`, `useSeriesDetail.ts:82-94`), поэтому старый owner object достижим в новой auth-сессии.
**Фикс (направление).** Передавать current auth uid, требовать `entity.userId === auth.uid`, key всех detail caches/listeners по `{uid,docId,authEpoch}` и detach до показа данных при auth transition.

### Confirmed draft может остаться и позже предлагаться как «несохранённый» — P1 (adversarial review 2026-07-25)
**Был/Эффект.** Если server commit успел, а вкладка упала до `markSaved`, при следующем открытии stored draft равен server value. Страница скрывает offer как identical (`studies/[id]/page.tsx:757-763`), но hook не удаляет recovered entry: `ourDraftRef` у нового instance равен null, поэтому confirmed-equal `persist` ничего не очищает (`useDurableDraft.ts:122-132,138`). После более поздней remote-правки этот старый уже подтверждённый текст снова будет предложен как unsaved.
**Фикс (направление).** После server-authoritative snapshot exact-equal stored version можно пометить acknowledged/retire; хранить version metadata, а не угадывать происхождение по одному mutable value.

**Фикс.** Явный `await Promise.resolve()` в начале `performSave` с комментарием, объясняющим зачем. Точнее было бы не зависеть от тайминга рендера вообще (передавать значения в сохранение явно), но это большая переделка автосейва — оставлено как направление.

### Долговечный черновик: переход МЕЖДУ документами не сбрасывает недописанный черновик — P2, ОТКРЫТ (найдено 2026-07-25 ревью-чтением)
**Был/Эффект.** `useDurableDraft` пишет черновик с задержкой 250 мс и дополнительно сбрасывает его при `pagehide`, сворачивании вкладки и размонтировании. Но переход с одного документа на другой ВНУТРИ приложения (`/studies/a` → `/studies/b`) хук НЕ размонтирует: меняется только ключ. При этом срабатывает лишь очистка таймера (`frontend/app/hooks/useDurableDraft.ts:126-130`), а сброс висит на эффекте с пустым списком зависимостей (`:133-155`) и не выполняется. Итог: текст, набранный в последние ~250 мс перед переходом, в черновик не попадает.
**Не регрессия.** В HEAD черновиков нет вовсе, так что хуже не стало — но заявленный инвариант «черновик есть ⟺ текст не подтверждён» в этом окне не держится.
**Фикс (направление).** Отдельный эффект на смену ключа, сохраняющий ПРЕДЫДУЩИЙ ключ с его же значением. Ловушка: к моменту выполнения эффекта `valueRef` может уже содержать значение НОВОГО документа — записать его под старым ключом означало бы подсунуть чужой текст. Нужна пара «ключ+значение», зафиксированная синхронно при рендере, и тест именно на переход A→B без размонтирования.

### Freshness-rollout: CAS до durable draft создаёт новые потери текста — P1, ОТКРЫТ (static review 2026-07-25)
**Суть.** Ожидаемый отказ устаревшей записи сейчас приходит ПОСЛЕ того, как несколько UI уничтожили единственную редактируемую копию: молитва вызывает `mutate()` и немедленно резолвит wrapper (`usePrayerRequests.ts:250-265`), после чего страница показывает success и закрывает modal (`prayers/[id]/page.tsx:135-139`); dashboard sermon modal вызывает `onClose()` ДО `await onSaveRequest` (`EditSermonModal.tsx:74-89`), а поздний `onError` восстанавливает целый старый sermon (`mutationDefaults.ts:574-577`). Поэтому включать CAS до durable draft/restore нельзя: чужой текст перестанет затираться, но свой будет теряться молча.
**Дополнительные блокеры протокола.** `groups/[id]/page.tsx:201-209` при любом autosave отправляет сразу все content-поля, а `useGroupDetail.ts:105-118` пишет fire-and-forget; production plan editor сохраняет полный `plan` через Admin API (`planApi.ts:55-67` → `sermons/[id]/plan/route.ts:271-334` → `sermons.repository.ts:158-160`), хотя `plan` отсутствует в предложенном списке aggregate revisions; Firestore rules (`firestore.rules:30-58,70-74,88-95`) проверяют ownership, но не revision, поэтому старые/обходные writers остаются разрешены.
**Гейт исправления.** Сначала durable draft/outbox + восстановление после reload для каждого editor, затем единый протокол для ВСЕХ writers данного aggregate (включая Admin/offline/delete) с version gate/rules, и только потом включение CAS и listener UX.

### CAS заметки доверяет свежей revision при старом тексте и разрешает затирание — P0, ОТКРЫТ (adversarial review 2026-07-25)
**Механика.** `serverRevisionRef` объявлен как версия, от которой построен текст (`studies/[id]/page.tsx:755-760`), но listener безусловно двигает его на версию каждого серверного снимка (`:831-849`), не применяя этот снимок к полям редактора. Поэтому последовательность `редактор=v0 → локально набран L → сервер принимает R/rev1 → listener ставит ref=1, поля остаются L → autosave шлёт L с expected=1` проходит CAS и тихо затирает R (`:267-280`; `conflictSafeUpdate.client.ts:93-100`). Интерфейс конфликта не появляется.
**Минимальный фикс.** Разделить `displayed/baseRevision` и `latestRemoteRevision`; listener не имеет права двигать первую без `applyRemote`. Rebase/«оставить моё» должен быть отдельной явной операцией на точную `actualRevision`.

### Persisted replay заметки теряет expectedRevision и обходит CAS — P0, ОТКРЫТ (adversarial review 2026-07-25)
**Механика.** Живой mutation принимает и передаёт `expectedRevision` (`useStudyNotes.ts:52-65`), но resumable mutation default после reload деструктурирует только `{id,updates,userId}` и вызывает `updateStudyNote` без версии (`utils/mutationDefaults.ts:424-427`). PersistQueryClient сохраняет и возобновляет paused mutations (`QueryProvider.tsx:79-92`). После reload та же операция становится обычным `updateDoc`, не bump'ит `rev.note` и может молча заменить более новый текст.
**Минимальный фикс.** Включить `expectedRevision` в persisted variable contract и replay; при stale показывать/сохранять конфликтный intent, никогда не downgrade'ить его до unguarded write.

### Revision ledger не является общим протоколом writers — P0, ОТКРЫТ (adversarial review 2026-07-25)
**Механика.** Guard группы недостижим через экспорт: `updateGroup` не принимает revision и всегда вызывает private writer без третьего аргумента (`groups.service.ts:254-260`); production hook тоже передаёт только два (`useGroupDetail.ts:105-118`). В sermon `core` guarded только `SermonHeader`, но тот же aggregate меняют без bump `EditSermonModal` (`:97`), `OptionMenu` (`:190,211,263`), sermon page (`:1206`), preparation writer (`sermons.client.ts:229-255`) и server/Admin writer (`api/repositories/sermons.repository.ts:53-64`). Series meta также имеет unguarded writers (`useSeries.ts:102-105`; `utils/mutationDefaults.ts:299-302`). Rules проверяют ownership, но не изменение revision (`firestore.rules:30-53`). Такой счётчик может оставаться прежним после изменения данных, поэтому следующий stale guarded writer получает ложное разрешение.
**Минимальный фикс.** Один обязательный writer protocol на aggregate: любой data-change атомарно bump'ит revision, любой edit intent указывает base revision; старые клиенты/серверные маршруты либо мигрируются, либо временно не смешиваются с CAS-claim.

### Guarded save ухудшает offline queue и series может остаться на старой revision — P1, ОТКРЫТ (adversarial review 2026-07-25)
**Механика.** HEAD использовал `updateDoc`; guarded `SermonHeader` и `useSeriesDetail` теперь используют `runTransaction`, которая офлайн падает и не попадает в нативную очередь. У series helper bump'ит серверный `rev.meta`, но сервис возвращает локальный `current` без нового `rev` (`series.service.ts:122-127`). Затем `refetch()` и invalidation по умолчанию не бросают при сетевой ошибке (`useSeriesDetail.ts:101-109`), поэтому UI может считать сохранение успешным и закрыть modal, сохранив в кэше старую revision; следующая легитимная правка будет отвергнута до успешной синхронизации.
**Минимальный фикс.** До durable intent/outbox не заменять queued `updateDoc` на transaction в офлайн-редакторах; после commit возвращать модель с новой revision и проверять `refetchResult.isError` либо использовать `throwOnError: true`.

### Плашка конфликта заметки не ставит autosave на паузу — P0, ОТКРЫТ (adversarial review 2026-07-25)
**Механика.** При `StaleWriteError` автосейв только вызывает `onConflict()` и возвращается (`studies/[id]/page.tsx:281-289`); родитель превращает это в `setSaveConflict(true)` (`:798-804`). Сам `useNoteAutoSave` не получает `saveConflict` и его effect продолжает запускаться на каждое изменение полей (`:298-304`). Если человек продолжает печатать, новая попытка идёт ДО выбора «оставить моё / взять чужое». Когда listener уже продвинул `revisionRef`, она проходит CAS и молча заменяет remote; когда не продвинул — снова конфликтует.
**Минимальный фикс.** После первого stale блокировать все фоновые save до явного решения; хранить отвергнутый immutable intent `{payload,baseRevision,actualRevision}`. «Оставить моё» отправляет именно этот (или явно подтверждённый текущий) intent один раз против `actualRevision`; дальнейший stale снова требует решения.
