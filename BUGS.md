# BUGS.md — трекер багов

> **Что здесь лежит:** только то, что **сломано сейчас**. Сломано/неверно → сюда, с якорем `file:line` + severity (P0/P1/P2/P3). «Хорошо бы добавить» → `FEATURE_CONCEPTS.md`.
>
> **Починил → УДАЛИ запись целиком.** История починенного живёт в git — `git log -p BUGS.md` и сообщения коммитов; дублировать её здесь нельзя, иначе секция перестаёт отвечать на вопрос «что сломано».
>
> **Форма записи — коротко.** Заголовок с ID и симптомом · строка якорей · две-три строки «ожидалось / получилось / чем сейчас является». Держись примерно в 300 знаках прозы на запись. **Карта класса — таблицей, в лимит не входит:** она чек-лист закрытия, и пока в ней есть непочиненные строки, запись не удаляется.
>
> **Чего здесь НЕ должно быть:** гейты с числами тестов · regression proof · живые замеры «до/после» · отвергнутые варианты · журналы ревью · стадия «починено локально». Всё это принадлежит журналу дела (`el log`, `CLAUDE.md` §3) и сообщениям коммитов. Трекер отвечает на «что сломано», а не «как чинили».
>
> **Спорный статус — в «Требует перепроверки», а не в «открыто».** Если одна запись говорит «открыт», а работа рядом говорит «закрыт», это не состояние бага, а неизвестность: её проверяют кодом, а потом переносят.

### BUG-20261030-analysis-reshape-loses-moved-work · При смене объёма стихов работа из убранных стихов может не дойти до соседнего разбора, а из своего уже уйти
**P1** — тихая потеря разрезов и связей. Найдено Codex 30.10 (ревью записи через форму), подтверждено кодом. Не закоммичено. **Якорь.** `frontend/app/components/bible/analysis/useAnalysisReshape.ts` — укороченный разбор и соседний, куда уходит работа убранных стихов, пишутся двумя отдельными разовыми командами (`updateNote` / `createNote`), отказ второй глотается (`.catch(() => undefined)`), а экран говорит «присоединено к …».
**Шаги.** Разбор A с разрезами в последнем стихе, за ним разбор B, у B висит неразрешённый конфликт → «Изменить объём», убрать последний стих A → A укорочен, запись в B отказана `decision-required` → работа последнего стиха нет ни в A, ни в B.
**Как должно работать.** Работа из убранных стихов либо оказалась в соседнем (или своём новом) разборе, либо осталась в старом — третьего нет; не удалось — экран говорит об этом и ничего не убирает.
**Направление.** Одно атомарное действие на оба документа (`.howto/save-several-documents-atomically.md`), а не две разовые команды; либо сначала надёжно записать получателя, потом укорачивать. **Класс:** перенос в соседний разбор и выделение в новый — оба пути `keep()`.

### BUG-20261030-analysis-other-bible-overwrite · Разбор, открытый в читалке другого перевода, ложится на чужие слова, а первая правка перезаписывает его под этот перевод

Найдено слепой охотой Codex 30.10 (дело `2026-10-12-block-diagram`, 3.41), подтверждено чтением кода; живьём не воспроизводилось. Не закоммичено — живёт в рабочем дереве с 3.4. **Якорь.** `frontend/app/components/bible/analysis/useAnalysisNote.ts` — слова берутся из `text` читалки (её перевод), а заметка открывается по id из списка «Моё» (`MineSheet.tsx:79`), куда разборы попадают из всех переводов (`utils/scriptureUsage.ts:120`); запись кладёт `bible` и число слов читалки поверх (`storedAnalysis(next, bible, total)`).

**Как должно работать.** Разбор открывается в своём переводе — там, где его слова. Из читалки другого перевода он открывается переключением на свой перевод (или только для чтения с кнопкой «Открыть в Синодальном»); правка никогда не перезаписывает разбор под чужой текст.
**Класс (механизмом):** «номера слов разбора читаются против текста, который не тот, на котором они сделаны». Места: открытие из «Моё» (поражено) · перенос объёма (`useAnalysisReshape.ts`, текст читалки — поражено тем же) · отображение структуры в «Моё» (`analysisOutline` читает сохранённый текст заметки — не поражено).

### BUG-20261030-analysis-write-over-newer · Изменение разбора с другого устройства, пришедшее в черновик, пока своя правка экрана ещё в пути, затирается этой правкой
**P1** — тихая потеря чужой правки (разрез, привязка, связь); окно узкое. Найдено Codex 30.10, подтверждено кодом. Не закоммичено. С 30.10 разбор пишет через одну форму движка (`useAnalysisNote.ts` `lay`, `form.commit`): правки идут цепочкой по свежему черновику, экран принимает черновик, только когда своих правок в пути нет. **Остаток.** `lay` кладёт в черновик разбор целиком, посчитанный от состояния экрана: изменение с другого устройства, слитое движком в черновик между последним приёмом и этой правкой (то есть пока прошлая правка экрана в пути), перезаписывается.
**Шаги.** Ноутбук: две правки подряд быстрее ответа сервера → в этот момент приходит связь A с телефона и сливается в черновик → вторая правка ноутбука кладёт разбор без A.
**Как должно работать.** Обе правки остаются: они меняют разное. Накрывает одна другую — экран говорит, ничего не стирает молча.
**Направление.** Класть в черновик не значение, а действие: повторить операцию правки (`cutAt`, `relateWords`…) над разбором из черновика внутри `commit(updater)`; либо слияние по ключам связей и привязок там же. Слияние движка (`mergeFields`) экрану брать нельзя — граница движка (`__tests__/architecture/dataEngineBoundary.test.ts`). **Класс:** разрезы, привязки, связи — один путь записи.

### BUG-20261030-analysis-merge-across-reshape · Связь или привязка, сделанная без сети, после переноса начала отрывка на другом устройстве встаёт на другие слова
**P1** — тихое смещение работы на чужие слова. Найдено Codex 30.10, подтверждено чтением слияния движка. Не закоммичено. **Якорь.** Номера слов считаются от начала отрывка; `relations` и `links` хранятся картами (`useAnalysisNote.ts` `storedAnalysis`), а движок сливает карты по ключам (`data-engine/protocol.ts` `mergeFields` → `mergeObjects`): ключ «2-5» с телефона ложится в разбор, где ноутбук уже сдвинул все номера, добавив стих спереди (`useAnalysisReshape.ts`).
**Шаги.** Телефон без сети: связь «слово 2 → слово 5» → ноутбук: «Изменить объём», добавить стих перед отрывком → телефон в сети → связь соединяет слова добавленного стиха.
**Как должно работать.** Действие на телефоне было раньше переноса; после встречи копий связь стоит на тех же словах, что видел человек (сдвинута вместе с отрывком), или, если это не установить, экран говорит о конфликте — но не переставляет её молча.
**Направление.** Привязать номера к началу отрывка: хранить начало рядом с позиционными данными и пересчитывать при чтении (сдвиг = слова между старым и новым началом), либо сделать начало частью пути данных, чтобы встреча с переносом становилась конфликтом. **Класс:** `relations` (поражено), `links` привязок (поражено), `cuts` (список чисел — встреча даёт конфликт, не поражено).

### BUG-20261029-older-tab-close-overwrites-newer-draft · Закрытая позже старая вкладка заменяет на устройстве более новый несохранённый текст другой вкладки
**P1** — теряется несохранённый текст; редко: нужны две вкладки одной заметки или окна комментария и отказ сохранения в обеих. Найдено Codex 29.10 при ревью BUG-20261028-typing-over-draft-offer; было и раньше. **Якорь.** `frontend/app/hooks/useDurableDraft.ts` — `persist` при закрытии вкладки (`pagehide`, размонтирование) снова пишет в общий слот текст редактора, хотя тот уже записан и слот с тех пор заняли слова другой вкладки.
**Шаги.** Открыть заметку в двух вкладках → в первой набрать A, во второй позже B (сохранение отказано, например без сети) → закрыть вторую, потом первую → открыть заметку: предлагается A, B пропал. **Ожидалось:** предлагается B — последнее действие человека.
**Как должно работать.** Слот хранит слова последнего действия человека на этом устройстве; повторная отправка тех же слов при закрытии вкладки — не действие. Новые слова, набранные после записи, сохраняются всегда — даже если слот снят сохранением или занят другой вкладкой.
**Направление.** Хранить с черновиком время нажатия, а не записи: у вкладок одного устройства общие часы; запись при закрытии не заменяет черновик с более поздним временем нажатия. Три попытки решить сравнением слов или признаком «что-то изменилось» (Codex r2–r4, 29.10) рождали новые случаи потери; тесты, которые решение обязано сохранить, — `frontend/app/hooks/__tests__/useDurableDraft.test.tsx` («Words typed are stored however the slot was left»).

### BUG-20261020-engine-sync-reads-more-than-changed · Движок, похоже, читает и перезаписывает больше, чем изменилось; обсудить с владельцем
**P1** — по слову владельца 20.10: чтения тратят дневную квоту базы (BUG-20261019-prod-firestore-quota-exceeded), а каждая лишняя запись на устройство — транзакция, которую Safari может заморозить (BUG-20261020-released-page-back-says-local-failure).
**Найден.** 2026-10-20 · вопрос владельца при разборе «Назад»; со стороны агента — чтение кода, замера чтений нет.
**Модель владельца (как должно быть).** На сервере и на устройстве есть «снимок-оглавление»: по каждой коллекции — её отпечаток (версия или хэш). Устройство держит последний серверный. Пришло оповещение «база изменилась» (или редкий опрос) → сравнили оглавления → знаем, какая коллекция и какие документы поменялись → вытянули только их и заменили в IndexedDB. Поработал на iPad, через два месяца на вебе поправил одну проповедь, открыл iPad — один раз подтянулась одна проповедь, больше ничего. Отправка — так же: уходит только изменённое.
**Что уже есть в движке (похоже на эту модель).** Голова коллекции с номером версии — `frontend/app/data-engine/feed.ts:6` (`collectionHeadRef`) · курсор «до какой версии я знаю» на устройстве — `collectionCursors.client.ts` · лента «что изменилось после версии N» — `collections.ts:449-470` (`changes`) · подписка на голову — оповещение без опроса (`collections.ts` `startHead`).
**Что подозрительно.** Открытие любого списка ставит «нужен полный пересмотр» (`collections.ts:196`, `sweepDue = true`; `refresh` — `:253`), а пересмотр в смешанном режиме читает весь список (`collections.ts:385`, `:398`, `hydrate`) и перезаписывает каждый документ даже без изменений (`collections.ts:479`). Курсор пишется и тогда, когда сервер ответил «изменений нет» (`collections.ts:465`).
**Измерить до решения.** Сколько чтений базы и записей на устройство даёт: открыть главную на прогретом устройстве · открыть проповедь · вернуться через день, когда на другом устройстве изменилась одна проповедь. Число «до» — по каждому сценарию.
**Как должно работать для пользователя.** Открыл — сразу видно то, что лежит на устройстве. Изменилось на другом устройстве — подтянулось ровно изменённое, один раз. Ничего не изменилось — ни чтений сверх проверки «изменилось ли», ни записей на устройство.
**⛔ Обсудить с владельцем** — после замера: где движок уже совпадает с моделью, где расходится и чего стоит каждое расхождение.

### BUG-20261019-dev-servers-share-prod-db · Dev-серверы и проверки агентов работают на боевой базе и выбирают её дневную квоту
**P1** — у проекта один дневной лимит на всех: 50 000 чтений, 20 000 записей, 20 000 удалений (тариф Spark, остаётся по решению владельца 19.10). Проверки агентов на localhost тратят ту же квоту, что проповедник на проде. 19.10 к 04:57 PDT она кончилась, и прод до полуночи PDT не отдавал данные никому (BUG-20261019-prod-firestore-quota-exceeded). Это второй случай: 2026-09-23 37 забытых headless-вкладок вызвали `RESOURCE_EXHAUSTED` на минуту.
**Найден.** 2026-10-19 · расследование квоты, дело `2026-10-19-firestore-read-quota`, `artifacts/diagnosis.md`.
**Как устроено сейчас.**
- `frontend/.env.local` (не в git, `.gitignore:52`) несёт настройки боевого проекта Firebase: `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, сервисный ключ `FIREBASE_SERVICE_ACCOUNT`. Любой `next dev` или `next start` в `frontend/` берёт их по умолчанию.
- Сервер: `frontend/app/config/firebaseAdminConfig.ts:19` поднимает Admin SDK с этим ключом. Ключ даёт полный доступ к базе в обход правил безопасности. На эмулятор сервер переходит, только если в окружении процесса задан `FIRESTORE_EMULATOR_HOST`.
- Браузер: `frontend/app/config/firebaseClientDb.ts:40` подключает эмулятор только при `NEXT_PUBLIC_FIRESTORE_EMULATOR=true`; без флага идёт в боевую базу.
- Рабочие копии агентов (`~/.codex/worktrees/*`) получают копию `.env.local`: на 19.10 она есть в двух из трёх.
- Тестовый пользователь `testuser@example.com` живёт в боевой базе. Данные, которые агенты заводят и сносят, тратят ещё и квоты записи и удаления.
**Почему так сложилось.** Одна база была с самого начала. Проект ведёт один человек, проверка на localhost шла его руками в нескольких вкладках, и квоты хватало с запасом. Нагрузку подняло не приложение, а способ работы. Агенты (Claude, Codex) ведут многочасовые автономные проверки в автоматизированных браузерах: десятки вкладок, свежий профиль на каждый сценарий (он заново перечитывает весь аккаунт), работа ночью. Открытая вкладка проверяет каждый наблюдаемый документ через сервер раз в 2 минуты, это около 190 чтений в час на вкладку. Десять вкладок за сутки дают около 45 000, почти весь дневной лимит. Пауза «10 минут без касаний» (`frontend/app/data-engine/browser.client.ts`, `ATTENTION_MS`) автоматизацию не останавливает: скрипт и есть касания. Эмулятор Firestore появился в проекте позже и как исключение для демо (`.howto/run-a-demo-on-the-emulator.md`, 19.10), а не как основа dev-среды.
**Что уже сделано и чего это не решает.** Убраны два бесконечных 15-секундных опроса (`frontend/app/data-engine/observer.ts`, 6bbb4a3a). Codex получил сообщение с правилами работы, и его стенд с 19.10 14:00 сам проверяет, что сервер читает эмулятор. Расход ниже, и этот агент сейчас в безопасности, но умолчание то же. Новый агент, новая рабочая копия или забытый браузер снова пойдут в боевую базу. Защита держится на дисциплине и уже подвела дважды.
**Как должно работать для пользователя.** Проповедник на проде получает данные всегда. Работа агентов на localhost не может выбрать его дневной лимит или тронуть его записи. Живая проверка агента не тратит боевую квоту по построению, а не по договорённости.
**⛔ Решение владельца — обязательно до фикса.** Это выбор цены, а не инженерная деталь: чего проверки агентов перестанут видеть и сколько стоит настройка. Агент, который берёт эту запись, не выбирает вариант и не меняет `.env.local` сам. Сначала он синхронизируется с владельцем: показывает варианты ниже на примере его работы и получает выбор. Затем записывает «Решение владельца ГГГГ-ММ-ДД» сюда и в журнал дела `2026-10-19-firestore-read-quota`, и только после этого чинит.
- **Эмулятор по умолчанию для агентов** (рекомендация агента 19.10). Без явного флага dev-сервер запускается против эмулятора и отказывается стартовать с боевым ключом; боевая база доступна только по явному разрешению. Плюс: квота не тратится вовсе, тестовые данные заводятся и сносятся свободно, агент не дотягивается до настоящих записей. Цена: эмулятор стартует пустым, поэтому нужен общий скрипт тестовых данных. Эмулятор не во всём равен облаку: он не требует составных индексов и отвечает с другой скоростью, такие расхождения поймает только прод.
- **Отдельный dev-проект Firebase на Spark.** Плюс: настоящее облако, где индексы, правила и сеть как на проде, и своя квота 50 000. Цена: завести проект, ключи, правила и индексы и держать их в согласии с боевыми; второй набор тестовых пользователей. Агенты могут выбрать уже его квоту, и до полуночи остановятся их проверки, но не прод.
- **Оставить как есть плюс правила работы.** Плюс: ничего не делать. Цена: защита только на памяти каждого агента, она подвела 23.09 и 19.10.

### Cross-account утечка persisted-кэша (общий компьютер)
**P2** — после logout данные предыдущего аккаунта могут отрисоваться следующему человеку на том же компьютере · `frontend/app/utils/queryPersister.ts:7` · `frontend/app/hooks/useAuth.ts:39-55`
Воспроизведено вживую: вышли из аккаунта A, вошли B, открыли прямой ссылкой проповедь A → на экране содержимое A, при этом `/api/me/entitlement` вернул 401. Источник — persisted React Query cache в IndexedDB, один глобальный ключ на все аккаунты; `handleLogout` его не чистит. Firestore Rules тут бессильны: они гейтят серверное чтение, а не локальную копию.
Ключ детали разведён по владельцу (`queryKeys.ts` → `['sermon', uid, id]`) — это второй слой, не закрытие. ⛔ НЕ «чистить кэш при смене uid» — пробовали и откатили: удаляло persisted paused-мутации, то есть несинхронизированные офлайн-правки. Правильное направление — **разделять, а не стирать**: партиционировать ключ персистера по uid, свой QueryClient на владельца, не восстанавливать persist-провайдер до резолва auth.
**Сделано 2026-10-03 (частично, запись открыта).** Закрыты два пути до экрана: чтение документа движка отвергает чужого владельца (`data-engine/transport.client.ts`), и одиночные чтения Firestore SDK, идущие на экран, считают чужой документ «не найден» — в обеих ветках гонки с сервером (`services/ownerListRead.client.ts` `ownedBy`: проповедь, серия, группа, молитва; правила Firestore разрешают эти чтения только владельцу, так что законного чужого чтения проверка не отрезает). Щели этих двух проверок: документ без поля `userId` пропускается, и пока вход ещё не восстановлен, чтение проповеди и молитвы не сверяет владельца. Рецепт: `.howto/keep-accounts-apart.md`.
**Почему открыта.** Три круга независимого ревью подряд находили новый путь того же класса: каждое хранилище устройства (кэш воркера, кэш Firestore SDK, сохранённый кэш запросов, свои IndexedDB) общее для всех аккаунтов, и защита держится на том, что каждая точка чтения помнит про владельца. Это петля заплаток, а не сходящийся фикс.
**Что осталось видно.** (1) Кэш сервис-воркера: `defaultCache` Serwist хранит GET `/api/*` в общем кэше `apis` (NetworkFirst, 10 с) и при обрыве сети или медленном сервере отдаёт B ответ, полученный A (`frontend/app/sw.ts`). Запрет кэша для приватного API пробовали и откатили: у части экранов нет другой офлайн-копии (счётчик рефералов в настройках). (2) Ключи кэша деталей серии, группы, молитвы и дат служения без владельца: при выходе A и входе B в той же вкладке шапка серии может показать название серии A. Смену ключей пробовали и откатили: без переноса старых копий она прятала у человека его же сохранённые данные офлайн после обновления. (3) Черновики аудиозаписей (`frontend/app/utils/recordingDraftStore.ts`) не знают владельца: B может прослушать запись A на странице того же контекста. Пометку владельцем пробовали и откатили: запись, расшифровка которой упала уже после смены аккаунта, метилась новым владельцем и пропадала у автора, а фильтр сбивал воспроизведение. (4) Копии данных прошлого владельца в хранилищах устройства (видны инструментами разработчика).
**Сюда слит** BUG-20260813-detail-caches-not-account-scoped (ключи деталей без владельца и общий кэш воркера — пункты (1) и (2) выше). С 2026-10-03 сохранённый кэш запросов хранится без срока (BUG-20260930-legacy-cache-week-expiry): копии прошлого аккаунта больше не удаляются по недельному лимиту. ⛔ Ключ с владельцем вводить одним конструктором для всех читателей, писателей и сбросов кэша одной коллекции и с живой проверкой смены аккаунта — иначе расколотый кэш даст порчу хуже утечки.
**Инженерная задача.** Разделять подтверждённые данные и несинхронизированную работу по владельцу через общий механизм, не стирать всё при смене аккаунта. Один человек в основном сценарии не разрешает показывать данные другого аккаунта. Для старых копий переносить только доказанную принадлежность; спорное сохранять без публикации под другой личностью. Нужна живая матрица вход/выход/офлайн после подготовки, а не вопрос о принятии утечки. Отдельная работа; риск не принят этим обсуждением.

Переиспользовать редактор движка либо расширить его существующий шов, без второго независимого журнала. Старые записи без доказательства исхода не стирать по догадке. ## ⚪ Осознанно НЕ чиним (решения владельца)
- **Лимит AI: перерасход у жёсткого потолка в пределах одного допущенного действия** (бывшая B9, TOCTOU). Проверка (`createUsageAdmission` / `assert*Available` в `frontend/app/services/usageLimits.server.ts`) и списание (`consumeUsage`, транзакция) — разные шаги: N вызовов, начатых при «потолок − 1», проходят все, а одно допущенное действие может списать больше одной единицы (мысль — до трёх попыток, `thought.structured.ts`; экспорт озвучки — все порции одного экспорта, `audio/generate/route.ts`). Решение владельца 2026-07-14 (F7 «по благодати»): жёсткий блок ровно на лимите не нужен — начатое доигрывается, новые после лимита идут в грации до «лимит + 10 %» (минимум +2), на потолке — блок с тёплым сообщением; малый перерасход допустим по построению. Грация построена в `c9e376b0`; закреплена `frontend/__tests__/services/usageLimits.server.test.ts` (warning → grace → blocked; начатое ниже потолка допускается) и `usageLimits.test.ts`. Не путать с обходом потолка продолжениями экспорта — это отдельная запись BUG-20261003-audio-continuation-skips-limit.
- **Порядки служения: слова живут в памяти страницы до подтверждения сервера.** Один узел, четыре следствия: (1) `pagehide`/unmount ЗАПУСКАЕТ запись, но транзакции нужен сервер — процесс, убитый в ту же секунду, уносит текст; (2) браузер online, а Firestore недостижим (captive portal, умирающая связь) — запись падает громко, текст остаётся в поле, но reload его теряет; (3) отказ в сохранении названия оставляет напечатанное только в DOM; (4) удаление шага, пересчитанное на свежем документе, уносит слова, дописанные туда другим устройством. Экран в каждом случае ГОВОРИТ об отказе — молчаливой потери нет. Лечение у всех четырёх одно: журнал операций на уровне шага (durable intent до записи, снятие только по подтверждению). Заплатка в одном месте не сходится — Codex три раунда подряд выдавал P1 в этом же узле; узел вынесен в отдельную работу сознательно.
- **Порядки служения: два устройства правят ОДИН И ТОТ ЖЕ шаг** — побеждает последний. Транзакция пересчитывает патч на свежем документе, поэтому разные шаги одного служения сливаются верно; совпадение поля в один и тот же момент — та же мерка, что и у мысли: система для человека, который через часы продолжил на другом устройстве. Настоящее лечение — журнал операций на уровне шага, отдельная работа.
- **Порядки служения: создание, удаление, «завести типовые» и разрядка рангов офлайн запрещены** — не «не успели», а решение. `addDoc` офлайн не отвечает вовсе (кнопка крутилась бы вечно), а очередь на удаление вернулась бы через час и унесла то, что тем временем написало другое устройство. Всё, что пастор ПИШЕТ, офлайн доступно.
- **Порядки служения: удаление не сверяет ревизию** — пастор может удалить обряд, в который другое устройство только что дописало слова. Диалог подтверждения есть, ревизионного предусловия нет; так же устроены все остальные удаления в приложении.
- **Порядки служения: перестановка — последний писатель побеждает** (`serviceOrders.client.ts:191`). Речь о ПОРЯДКЕ карточек, не о тексте: расходится расстановка, а не слова.
- **Порядки служения: сбой посреди перенумерации может оставить порядок наполовину переставленным** (бывшая BUG-20261003-service-orders-renumber-partial-failure, решение владельца 2026-10-11). Нужны тесные ранги (`needsRenumber`) и отказ одной из записей серии (`useServiceOrdersEngine.ts` `moveOrder`): порядок b,c,d,a вместо прежнего или задуманного. Страдает расстановка карточек, не слова; она видна и правится перетаскиванием; после первой удачной перенумерации ранги разнесены, и перенос пишет один документ. Лечение — одна атомарная команда на все ранги (новый вид серверной связи по образцу `council-carry`) — объём фичи, не строим.
- **Настройки не входят в схему версий** — каждый писатель в `userSettings.service.ts` отправляет только изменённое поле через `setDoc(merge)`. Два устройства над разными настройками не пересекаются по построению; одна и та же настройка — это тумблер, значение которого человек видит и возвращает. Скрытого текста там нет, защита добавила бы только ложные конфликты.
- **Одна и та же секция плана с двух устройств — последний писатель побеждает.** Разные секции больше не сталкиваются (каждая пишется отдельным вложенным путём `plan.<секция>`), но внутри одной секции заявленной версии нет.
- **Правка той же мысли с двух устройств в пределах окна ретрая транзакции** (доли секунды) — цена защиты выше цены риска. Мерка владельца: система для человека, который через ЧАСЫ продолжил на другом устройстве, а не для скриптов, ловящих доли секунды.
- **share/notes viewCount** инкремент (`share/notes/[token]/route.ts:34`) — аноним накручивает чужой счётчик-тщеславие, ноль импакта.
- **share-links GET mismatch** (`share-links/route.ts:16`) — игнорит mismatched query `userId`, но возвращает СВОИ линки звонящего, не жертвы → не уязвимость, косметика.
- **Ссылка на заметку, созданная или отключённая без сети, уходит только при возврате к вкладке** (`frontend/app/hooks/useStudyNoteShareLinks.ts:44`, `:58`).
