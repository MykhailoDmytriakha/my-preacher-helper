### Правило `advancesRevision` — заготовка, а не «кнопка»: включение по чек-листу ПОЛОЖИТ приложение (2026-07-26)
**Был.** `frontend/firestore.rules:52-56` держит функцию `advancesRevision(aggregate)` закомментированной, а над ней — «ACTIVATION CHECKLIST (owner's call)» из трёх пунктов, который читается как «раскомментировать и выкатить». Проверка кодом показала, что чек-лист неполон в главном: **функцию неоткуда вызвать** — ни в одном `allow update` её нет, поэтому раскомментирование само по себе не даёт ни защиты, ни поломки (мёртвый код).

**Эффект — если подключить «в лоб».** При update `request.resource.data` — это **полное будущее состояние документа**, а не только присланные поля ([Firebase docs](https://firebase.google.com/docs/firestore/security/rules-conditions)). У проповеди счётчик `rev: {core, thoughts, outline, plan}`; правка одних мыслей поднимает только `rev.thoughts`, остальные три остаются прежними. Значит `advancesRevision('core')`, подвешенный к `allow update`, проверит `4 > 4` → ложь → **permission-denied на любой записи, которая этот агрегат не трогает**, то есть на большинстве. Бьёт по СЕГОДНЯШНЕМУ клиенту, а не по старому PWA, ради которого правило задумано.

**Отдельно — настройки.** `app/services/userSettings.service.ts` пишет через `setDoc(merge)` и счётчик не двигает ВООБЩЕ (осознанно: там нет набранного текста, только тумблеры и перечисления). Правило, распространённое на `users`, полностью ломает сохранение настроек.

**Фикс (направление).** Правило должно звучать как «изменились поля агрегата X → `rev.X` обязан вырасти», то есть опираться на `request.resource.data.diff(resource.data).affectedKeys()`, а не проверять агрегат безусловно. Порядок работ: (1) дописать подключение через `affectedKeys` для каждой коллекции, где схема версий действует; (2) явно вывести `users` из-под правила; (3) прогнать на эмуляторе Firestore rules — прод для этого не нужен; (4) только потом пауза на обновление залежавшихся PWA и выкатка по существующему чек-листу; (5) помнить, что Admin SDK правила обходит — серверные писатели защищены только собственной дисциплиной (`sermons.repository.ts` принимает имя агрегата).

**Статус риска сейчас:** ноль. Правило выключено и не вызывается, ничего не сломано; опасность появляется ровно в момент, когда кто-то последует чек-листу буквально.

### B9 · TOCTOU перебора usage-лимита при конкурентном burst
**Суть.** Проверка лимита и его инкремент — РАЗНЫЕ шаги. `assertAiUsageAvailable` читает-проверяет ДО провайдер-вызова, `consumeUsage` инкрементит ПОСЛЕ отдельной транзакцией, БЕЗ ре-проверки (`usageLimits.server.ts:105`, `:120` слепой `current+amount`). Два одновременных запроса на 99/100 оба проходят check → оба исполняются → usage уходит за квоту.
**Масштаб — СИСТЕМНЫЙ, 5 потребителей одного примитива:** `structuredOutput.ts:280`, `audio/generate:380`, `studies/transcribe:145`, `thoughts/route:233`, `thoughts/transcribe:144`.
**РЕАЛЬНЫЙ ИМПАКТ (оценка 2026-07-14).** Бьёт только при ИСТИННОЙ одновременности (окно check→increment = мс). Последовательные вызовы считаются корректно (каждый перепроверяет). Обычный UI-юзер: перерасход ~0; две вкладки/двойной клик → 1-2; целенаправленный параллельный burst → больше, но каждый жжёт реальный вызов провайдера и **самоограничивается** (после лимита всё блокируется). Малая база + щедрые квоты (100–5000) → **P1 по классу, но НЕ срочно**; чинить при работе над примитивом, не пожар.
**РЕФРЕЙМ (владелец 2026-07-14): грация, не жёсткий блок → фича.** Владелец НЕ хочет атомарного блока ровно на лимите. Пример: транскрибация = 2 списания (STT+полировка) → одно действие на 99 даёт 101, и это ОК «по благодати». Нужно: (1) действие ДОигрывается (не падает на полпути), (2) мягкий блок НОВЫХ действий за лимитом, (3) hard-cap на бо́льшем пороге (напр. limit+10%), (4) в настройках/админке при перерасходе — тёплое сообщение + СТИХ про благодать. ⇒ B9 из «гонки на устранение» → в **grace-band фичу** (`FEATURE_CONCEPTS.md` F7). Атомарность перестаёт быть критичной (малый overshoot — by design); остаётся hard-cap + сообщение.
**Фикс (направление, из Popper-петли):**
- **Дискретный `aiUsed` (+1, известен заранее):** atomic **reserve+refund ДО провайдера** (проверка+инкремент в одной `runTransaction`; бросок → 429 ДО стрима; refund при провале провайдера). ⚠️ простой rethrow НЕ проходит: `callWithStructuredOutput` (17 вызовов через 8 wrappers) глотает исключение в `{success:false}`/`[]`/500 — надо явно мапить `UsageExhaustedError`→429 на границе роута.
- **Seconds-метры (transcription, audio — сумма известна ПОСЛЕ):** assert(оценка) ДО + consume-actual ПОСЛЕ, БЕЗ throw (иначе после успешной генерации 500 → повторная оплата провайдера). Минимальный overshoot при burst допустим (щедрые квоты). Reserve-before НЕ рекомендован (плохо стыкуется с audio per-batch, риск refund-on-crash).

### RMW-класс · lost-update read-modify-write вне транзакции → ONLINE-гонка закрыта 2026-07-24; офлайн-replay, same-item merge и серверный путь ОТКРЫТЫ
**Суть.** Код читает документ, фильтрует/меняет ВЕСЬ массив в памяти из stale-read и `writeBatch`/`update` перезаписывает его целиком. `writeBatch` ≠ read-isolation → при конкурентном same-owner редактировании между read и commit правка теряется (или остаётся dangling-ссылка). Это НЕ точечный баг — это паттерн по всему коду.
**✅ Что реально закрыто (2026-07-24):** **7** клиентских сайтов переведены на `runTransaction` через `app/services/atomicUpdate.client.ts` → пока оба устройства онлайн, конкурентная правка больше не затирается. Покрыто ТОЛЬКО безопасное к повтору: добавления (thought create insert-if-absent · preachDate add по client-id · prayer update по updateId · group meetingDate add по mintedId) и удаления (thought · preachDate · group meetingDate). ⛔ Три update-пути (`updateThoughtViaClient`, `updatePreachDateViaClient`, `updateGroupMeetingDateViaClient`) СОЗНАТЕЛЬНО оставлены НЕ транзакционными: они мержат ПОЛНЫЙ объект от вызывающего, а SDK повторяет callback транзакции (до 5 попыток) даже когда коммит УЖЕ прошёл, а ответ потерялся — повтор наложил бы устаревший payload на более новую правку, то есть транзакция ДОБАВИЛА бы порчу, которой в HEAD нет.
**⏳ ОТКРЫТО #0 — «воскрешение» при повторе ADD (унаследовано от HEAD, не регрессия).** ADD закоммитился → ответ потерян → другое устройство УДАЛИЛО элемент → повтор видит свежий снимок без этого id и вставляет элемент снова. `insert-if-absent` не различает «никогда не добавляли» и «добавили, потом удалили». HEAD делал то же и вдобавок затирал добавленное другим устройством, то есть наш вариант класс СУЖАЕТ, но не закрывает. Полное закрытие = tombstone/ledger применённых операций.
**⏳ ОТКРЫТО #1 — офлайн-replay.** Правка, сделанная ОФЛАЙН, кладётся в очередь как устаревший полный массив; при реконнекте приходит последней и затирает то, что закоммитило другое устройство. Лечится durable-outbox с ID-операциями + rebase на реконнекте либо нормализацией горячих массивов в отдельные документы. См. `FIRESTORE_SYNC_RESEARCH.md` §6, §11a.
**⏳ ОТКРЫТО #2 — same-item merge.** `updateThoughtViaClient` принимает ПОЛНЫЙ stale `Thought` от вызывающего (`useSermonActions.ts:263-273`), поэтому при правке РАЗНЫХ полей одной мысли на двух устройствах stale-поля перетирают чужие (напр. `isLocked`). Лечится приёмом минимального field-patch вместо целого объекта.

### Cross-account утечка persisted-кэша (общий компьютер) — ВОСПРОИЗВЕДЕНО (2026-07-25)
**Воспроизведено вживую** (было теорией, стало фактом): в одном браузере вышли из аккаунта A, вошли тестовым аккаунтом B, открыли прямой ссылкой проповедь аккаунта A → **на экране отрисовалось содержимое A** (заголовок, дата, стих), при этом `/api/me/entitlement` вернул **401**, то есть СЕРВЕР данные НЕ отдавал. Firestore Rules тут бессильны: они гейтят серверное чтение, а не локальную копию.
**Эффект.** После logout данные предыдущего аккаунта остаются в браузере и могут отрендериться следующему пользователю на ТОМ ЖЕ компьютере (реальный сценарий: общий церковный ПК).
**Три якоря:**
- `frontend/app/hooks/useSermon.ts:59` — `queryKey: ["sermon", sermonId]` **без UID** (списки при этом с UID: `['sermons', uid]` в `useDashboardSermons.ts:50`) → ключ совпадает у разных аккаунтов.
- `frontend/app/utils/queryPersister.ts:7` — ОДИН глобальный ключ IndexedDB `react-query-cache` на все аккаунты.
- `frontend/app/hooks/useAuth.ts:39-55` (`handleLogout`) — чистит `localStorage.guestUser` + `sessionStorage`, но НЕ React Query cache и НЕ IDB-persister.
**Фикс (направление).** ⛔ НЕ «чистить кэш+persister при смене uid» — пробовали и ОТКАТИЛИ 2026-07-25: при выходе оно удаляло persisted paused-мутации (безвозвратная потеря несинхронизированных офлайн-правок, в том числе «вышел и зашёл тем же аккаунтом»), не трогало отдельный Firestore `persistentLocalCache` и не спасало от восстановления «бесхозного» payload до резолва auth. ✅ ПРАВИЛЬНОЕ направление — **разделять, а не стирать**: (1) ключ IDB-persister партиционировать по разрешённому uid (`react-query-cache:<uid>`), (2) свой QueryClient на владельца, (3) owner-uid + auth-epoch внутри persisted-конверта и отбраковка «опоздавшего» restore, (4) НЕ монтировать/восстанавливать persist-провайдер до резолва auth (anonymous uid — тоже полноценный владелец), (5) Firestore-кэш решать ОТДЕЛЬНО (`memoryLocalCache` по умолчанию либо координированный multi-tab terminate/clear, сохраняющий pending-записи), (6) uid в ключ детали (`["sermon", uid, sermonId]`) как второй слой.

## 🟠 Решение владельца — архитектура

### Архитектурная развилка: мелкие документы + одна обязательная граница записи (эскалация 2026-07-26)
**Как выросло.** Девять витков независимого ревью подряд: счёт P0 3 → 8 → 7 → 5 → 7 → 10 → 12 → 12 → 11. Каждый круг находил регрессии, внесённые фиксами предыдущего круга. Правило «растёт три витка → стоп и решение владельца» сработало; дальнейшее латание по списку — имитация работы. Журнал витков: `.sessions/SESSION_2026-07-26-freshness-popper-loop-journal.md`.
**Вердикт, совпавший у трёх независимых прогонов.** Корректность зависит от того, что КАЖДЫЙ вызывающий правильно передаст агрегат, версию, опору, uid, маршрут и нарисует разрешение конфликта — при том что независимо редактируемые данные лежат в больших массивных документах. Инвариант не обеспечен конструкцией, поэтому его приходится повторять руками в каждом экране, и каждая заплатка на краю UI рождает новый способ потерять текст.
**Две части решения.**
1. **Мелкие документы** — разнести независимо редактируемые части (план, наброски, мысли, подготовка) по отдельным документам либо ввести строгое владение полями. Тогда «два устройства над разными частями» не сталкивается по построению, а не за счёт дисциплины писателей.
2. **Одна обязательная граница записи** для ВСЕХ писателей агрегата: `{baseVersion, patch, operationId}`, включая Admin/серверные маршруты, офлайн-очередь и удаления. Офлайн — durable outbox, доигрывающий ТОТ ЖЕ протокол.
**Почему счётчика недостаточно.** Счётчик как токен сравнения корректен, но гарантия держится на дисциплине; хэш её не решает (его так же можно не проставить). Единой авторитетной границы записи в проекте нет.
**Что это разблокирует.** Записи «Незащищённые писатели проповеди», «`EditSermonModal`: защита откачена», «Группа: защита недостижима» — все три упираются именно в эту развилку, и по отдельности лечатся заплатками, которые петля уже отвергла.

## ⚪ Осознанно НЕ чиним (решения владельца)
- **Настройки не входят в схему версий** — каждый писатель в `userSettings.service.ts` отправляет ТОЛЬКО изменённое поле, запись идёт `setDoc(merge)` (`:54`). Два устройства над РАЗНЫМИ настройками не пересекаются по построению; одна и та же настройка — это тумблер, значение которого человек видит и возвращает. Скрытого текста там нет, защита добавила бы только ложные конфликты.
- **Одна и та же секция плана с двух устройств — последний писатель побеждает.** Разные секции больше не сталкиваются вообще (каждая пишется отдельным вложенным путём `plan.<секция>`), но внутри одной секции заявленной версии нет. Осознанно оставлено в пределах класса.
- **Правка ТОЙ ЖЕ мысли с двух устройств в пределах окна ретрая транзакции** (доли секунды) — не чиним: цена защиты выше цены риска. Мерка владельца: система для человека, который через ЧАСЫ продолжил на другом устройстве, а не для скриптов, ловящих доли секунды.
- **share/notes viewCount** инкремент (`share/notes/[token]/route.ts:34`) — аноним накручивает чужой счётчик-тщеславие, ноль импакта.
- **share-links GET mismatch** (`share-links/route.ts:16`) — игнорит mismatched query `userId`, но возвращает СВОИ линки звонящего, не жертвы → не уязвимость, косметика.
