# CLAUDE.md — главный вход для агентов этого репозитория

> Это **ГЛАВНЫЙ** файл инструкций проекта. `AGENTS.md` теперь только ссылается сюда.

## 0. Первым делом (на КАЖДОЙ сессии)
- **Загрузи skill Mike** (`/mike`), если он доступен, и работай в режиме Mike. Mike — это про то, **КАК** работать (способ, дисциплина), а не **ЧТО** делать. Прочитай тело скилла целиком ДО первого действия.
- **Если skill Mike недоступен** — держи принципы из раздела **§4 «Fallback: кто такой Mike»** ниже (самодостаточное описание способа работы).

## 1. Язык
- Общайся на русском или английском. **НЕЛЬЗЯ на украинском.**
- **ВЕСЬ КОД — НА АНГЛИЙСКОМ.** Разговор с пользователем идёт по-русски, но всё, что попадает в репозиторий как код, пишется по-английски: комментарии · имена переменных, функций, типов, файлов · названия и описания тестов (`describe`/`it`) · сообщения коммитов · тексты ошибок для разработчика. Русский в коде допустим ровно в одном месте — пользовательские строки в `frontend/locales/`. Причина простая: код читают инструменты, линтеры и следующие агенты, и смешанный язык делает его непригодным для поиска и ревью.
- Пользователь часто диктует голосом (Speech-to-Text) → возможны артефакты распознавания и в контенте, и в командах. Отвечай на **смысл/намерение**; не уверен на 100% — **уточни**, не иди на догадке.

## 2. Принципы Mike (кратко)
Порядок опор: **Совесть → Структура → Интеллект (команда) → Ответственность.**
- **Синхронизация ПЕРЕД действием:** первый запрос обычно сжат — сначала пойми вектор/намерение пользователя, синхронизируйся, не строй на догадке (перестройка дороже синка в начале).
- **Контекст ДО действия, по нарастающей:** пользователь → код/логи проекта → web (внешний факт) → вопрос пользователю последним.
- **Якорь, не прокси:** каждое утверждение — с проверяемым якорем (`file:line` / лог / число / источник).
- **Необратимое** (commit / deploy / delete) — стоп + подтверждение человека; перед принятием — независимая проверка/опровержение.
- **TaskList** — скелет на многошаговой работе; веди с начала и держи актуальным.
- **Flush на диск по ходу** — ход работы, факты и решения — в журнал дела через `el log` (раздел Elephant); знание на будущее — по правилу «Память» в §3. Контекст гибнет с сессией, файлы переживают.
- **Объясняй просто** — по-человечески, термин расшифровывай на месте, с примером/аналогией.

## Elephant — память работы в `.cases/`

Ты начинаешь без памяти, и следующий агент начнёт так же — у него будет только `el`. Чего нет в `el` — сделанного, решений, причин, — для него не существует. Форму держит `el`: порядок, отказы, подсказки; содержание — ты.

**Начало — `el`.** Первая строка `thread:` — цель → фаза → пункт → шаг. Перескажи владельцу не его словами: что из этого следует, чего он не сказал (помечай «вывожу»), что спросишь. Его же слова в ответ — эхо, а не понимание.

**Работа — пункт за пунктом.** **IMPORTANT: закончил пункт — сразу `el todo done N.M <вид> "что вышло"`, не в конце сессии** (вид — `file:путь` · `ref:след` · `run:"команда → исход"` · `owner`). Решение — `el log DECISION "что · вместо чего · почему"`. `.howto/` — что здесь уже умеют, по рецепту на задачу: берёшься за задачу — открой её рецепт, упёрся — `grep -ril "<слова ошибки>" .howto/`; решил новое — `el log PROBLEM` и рецепт `.howto/<глагол>.md` с первой строкой `when: <слова беды>`, чтобы следующий не решал заново. Не для этой фазы — `el todo add later "…"`.

**`el` подвёл — отзыв сразу, не спрашивая.** Отказал там, где работа права; строка без честной починки или врёт; пришлось обойти `el` или гадать — прервись и запиши `el feedback "…"`, пока точный вывод перед глазами (форма — `el help feedback`), и работай дальше обходом. Разрешения не нужно; в конце скажи владельцу, что отзыв лежит.

**Конец — снова `el`.** Order чист, State правдив: `el readme set next "…"`, а если всё верно — `el readme touch`. Сделанное принимает другая рука — свежая сессия или субагент с чистым контекстом: `el todo brief N.M` печатает ему задание; `[/]` в TODO — сделано, ждёт приёмки. `[/]` прошлой сессии принимаешь ты — для неё ты вторая рука: перезапусти каждое `run:` и принеси, что вышло сейчас — `el todo accept N.M --by <ты> --run "команда → исход" "…"`.

README, TODO, JOURNAL — только через `el`: правку руками ловит отпечаток. Строки `hint:` и `Order` — команды тебе, с номером: сделай или скажи, почему нет. Знание дозами: `el help start`, потом `el help <тема>`.

Нет `el` → `git clone https://github.com/MykhailoDmytriakha/elephant-cli`, затем `./elephant-cli/install.sh`.

## 3. Процедуры проекта (обязательные)
- **Память:** читай `MEMORY.md` в начале задачи — там принципы, соглашения, инварианты фич и карта кода; новое знание этих видов пиши туда же. Рецепт (как сделать операцию, что значит ошибка) — в `.howto/` по разделу Elephant: сначала дополни существующий рецепт, новый заводи только для ещё не описанной операции или проблемы. Разовые факты, решения и результаты проверок — в журнал дела.
- **⚠️ НЕ ПИШИ СВОЁ ПРАВИЛО, ПОКА НЕ ПОСМОТРЕЛ, ЧТО УЖЕ ЕСТЬ.** Собрался писать логику про свежесть данных, слияние двух копий, публикацию результата записи, офлайн, связь двух сущностей или цвет — сначала найди рецепт этой операции (раздел Elephant) и прочитай код, на который он ведёт. В строке `when:` рецепта есть английские и русские слова, но поиск идёт по буквам, а не по смыслу: пусто — попробуй имя из кода или английский термин и загляни в оглавление `head -1 .howto/*.md`; пустой поиск — ещё не доказательство, что механизма нет. Для чтения и изменения данных сначала проверь, переведена ли коллекция на data-engine (`frontend/app/data-engine/README.md`, `docs/architecture/data-engine-migration-log.md`): переведённая работает через `frontend/app/data-engine/react.client.tsx`, а не через внутренности движка или legacy-писателя. Вторая, чуть другая реализация общего правила — самая дорогая ошибка в этом репозитории: обе выглядят верными, чинят одну, а расхождение читается как чужая правка. Живой случай — запись 2026-08-17 в `MEMORY.md`: семь витков ревью на то, что уже лежало в `utils/`.
- **Баг-трекинг → `BUGS.md` · беклог фич → `FEATURE_CONCEPTS.md`** (оба в КОРНЕ репо). Полный жизненный цикл бага ведёт скилл **`bugs-fix`** (`.claude/skills/bugs-fix/SKILL.md`) — там форма записи, режимы работы, карта рисков стека и процедура закрытия; здесь только несущие правила.
  - **Обнаружил БАГ** (в т.ч. попутный — при ревью, фиксе, чтении кода) → **сразу** заводи запись в `BUGS.md`, в свою секцию по severity: `🔴 P1 — открыто` / `🔴 P2 — открыто` (нужен P0 — заводи секцию выше P1), в начало секции. Обязательно: ID вида `BUG-ГГГГММДД-краткий-slug` · якорь `file:line` · severity с причиной · ожидалось/получилось · шаги воспроизведения · эффект. **Плюс раздел «как эта фича должна работать с точки зрения пользователя»** — когда обязана срабатывать, когда обязана молчать: без него фикс лечит симптом.
  - **Спорное или невоспроизводимое** → `🔍 Требует перепроверки`, а не в «открыто». Не код-фикс и принятый риск — свои секции. Идея/расширение (не баг) → `FEATURE_CONCEPTS.md`. Разделяй по сути: сломано/неверно = баг · «хорошо бы добавить» = фича.
  - **Починил → УДАЛИ запись целиком** (секции «Исправлено» нет и не должно быть: трекер отвечает на вопрос «что сломано СЕЙЧАС»). Но сначала — **закрытие в журнал дела**: `el log RESULT "закрыт BUG-… · корень · что сделано · regression красный→зелёный · гейты · чем проверено живьём · остаточный риск"` (раздел Elephant). **Удаление едет одним change set с коммитом**, чьё сообщение несёт ID и суть: журнал в git не попадает, и без коммита след теряется совсем.
  - **Нашёл баг — прочеши класс.** Он почти никогда не единственный: назови механизм словами, найди все места, где он живёт, и по каждому скажи вслух «поражено / не поражено и почему». Поражённое того же класса чини в этом же заходе.
- **Вход в приложение для ручной проверки — РАЗРЕШЁН БЕЗ СПРОСА.** На лендинге в dev-режиме есть кнопка «Войти как тестовый пользователь»: она делает `signInWithEmailAndPassword` в УЖЕ СУЩЕСТВУЮЩИЙ dev-аккаунт `testuser@example.com` (`frontend/app/(pages)/page.tsx:64`, ветка `isDev`) — никакой аккаунт не создаётся, пароль зашит в код для локальной разработки. Владелец разрешил жать её самостоятельно. НЕ путать с `signInAsGuest` (`firebaseAuth.service.ts:68`) — там `signInAnonymously`, то есть новый анонимный пользователь + профиль-документ; её без спроса не трогать.
- **Web search** — базовый инструмент: тяни ниточку до первоисточника, не останавливайся на полпути.
- **Субагенты — только на модели на уровень НИЖЕ основной сессии.** Лестница: Fable → Opus → Sonnet → Haiku (Haiku — нижняя ступень, ниже некуда). Основная сессия на Opus → субагенту `model: "sonnet"`; на Sonnet → `model: "haiku"`. Параметр `model` в вызове Agent указывать **всегда**: без него субагент наследует модель сессии, а это ровно то, чего правило не допускает. `subagent_type: "fork"` всегда наследует модель сессии — поэтому форк не использовать. То же для агентов внутри Workflow.
  - **Почему:** субагенту отдаётся подзадача, а она по определению проще задачи основной сессии. Та же модель на подзадаче жжёт токены быстро и без пользы (живой случай 2026-09-28: приёмка на Opus-субагенте ушла на 222 тыс. токенов).
  - **Следствие для нарезки работы:** делегируй только то, что по силам модели ступенью ниже — поиск и сбор фактов, прогон тестов и сверку с доказательствами, механические правки по точному заданию, ревью по чётко названной цели. Решения, архитектура, развилки и финальная проверка остаются в основной сессии. Если задача требует той же силы мышления, это не задача для субагента: делай сам или отдай Codex по его скиллу.
- **AI-промпт-телеметрия:** при ревью AI-промптов сравнивай сырой вход/транскрипт с выходом (JSON/schema success ≠ качество); классифицируй дельту (корректная очистка / over-generation / under-generation). Scope — `frontend/docs/ai-prompt-telemetry-review-loop.md` → Review Baselines.
- **Стек:** Next.js 15 App Router · React 19 · TypeScript · Tailwind · Firebase/Firestore (client SDK, персистентность в IndexedDB) · React Query (offline-first) · react-i18next · PWA через Serwist; тесты Jest + Testing Library. Локали — **ВСЕГДА три**: `frontend/locales/{en,ru,uk}/translation.json`. ⚠️ Версии проверяй в `frontend/package.json`, а не по этой строке: здесь год стояло «Next.js 14», пока в проекте был 15.
- **Перед пушем в main:** `npm run test:fast` + eslint + `npx tsc --noEmit` (Vercel build гейтит и на тестах, и на типах).

## 4. Fallback: кто такой Mike (если skill недоступен)
**Mike — это способ работы, не ассистент-исполнитель. «The 150% Operator»: 100% точности исполнения + осознанность контекста. Истина и верификация важнее похвалы и комфорта.**
- **Совесть (истинолюбивая):** честно, соразмерно, ради пользователя; провал критерия → стоп, не обходить умом.
- **Структура (инженерная):** карта реальности до аналитики — акторы, ресурс, порядок, причина vs симптом, узкое место, чего НЕТ. Шаги минимальны и обратимы.
- **Интеллект (дедуктивный):** докапывайся до сути, проверяй, а не верь на слово; никаких гипотез без проверки.
- **Ответственность (подотчётная):** закрывай проверяемым, end-to-end как конечный потребитель; необратимое — человеку.
- **Ясность (как Фейнман):** объясняй предельно понятно, но технически безупречно; всегда проходи «extra mile».
- **TRIZ + IFR:** при архитектурном/UX-решении спрашивай «что система делает в идеале сама, без затрат/побочек?»; разрешай противоречия явно, фиксируй IFR → Противоречие → Решение.
