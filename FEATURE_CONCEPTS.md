### F7. Grace-band лимит usage — «по благодати» (владелец 2026-07-14)
**Идея.** Не жёсткий блок ровно на лимите, а МЯГКИЙ порог с грацией. Мотив: одно легитимное действие может стоить >1 (транскрибация = STT + полировка = 2 списания), и падать на полпути — плохой UX; дух приложения (помощник проповедника) → благодать уместна как продуктовая черта, не только техника.
**Поведение:**
- Действие, начатое в пределах лимита, **ДОигрывается целиком** (даже если перескочит на 1-2 — напр. 99 → 101).
- Мягкий блок **НОВЫХ** действий, когда лимит достигнут/чуть превышен.
- **Hard-cap** на бо́льшем пороге (напр. `limit + grace`, где grace = 10% или фикс) — дальше реально нельзя запустить новое.
- При перерасходе в настройках/админке — тёплое сообщение + **СТИХ про благодать** (напр.: «даже если мир нечестен — будьте честны и живите по благодати» / «Христос простил нам все долги»). Ротация нескольких стихов.
**Связь.** Заменяет строгий атомарный фикс **B9/TOCTOU** (`BUGS.md`) и закрывает старый residual F5 «TOCTOU soft-cap»: малый overshoot допустим **by design** → атомарность не критична; остаётся только hard-cap + grace-message. Реализация: soft limit (allow до `limit+grace`) + hard limit + UI перерасхода со стихом.

**Два уровня реализации:**
1. **Дёшево (только текст):** переформулировать i18n-ключи `pwa.updateAvailable.title/description` — явно «обновится приложение, данные не тронуты». Ноль новой инфраструктуры, снимает путаницу данные-vs-сайт сразу.
2. **Богато (changelog):** шеврон «Что нового» → раскрывается список изменений версии. Цена: компонент сейчас знает ТОЛЬКО «SW сменился» (boolean), про содержание изменений — ничего. Нужен источник release-notes на версию (JSON, вшитый в build) + дисциплина писать заметки на каждый deploy.

**Демо:** показан макет улучшенного попапа (сравнение сейчас/предложение, кликабельный шеврон) в сессии.

### Углубление (2026-07-19): реальный пробел — обновления ДАННЫХ невидимы, не только текст попапа

Копнули глубже — и оказалось, дело не в формулировке попапа, а в **асимметрии**:
- **Обновления ПРИЛОЖЕНИЯ** (новый deploy) → есть уведомление (`SwUpdateToast` на `controllerchange`).
- **Обновления ДАННЫХ кросс-устройство** (правка с телефона → десктоп) → **НИЧЕГО**: ни живого синка, ни уведомления, и текущий экран может показывать УСТАРЕВШЕЕ.

Механизм (по коду):
- `onSnapshot` нет нигде → нет real-time подписок Firestore.
- `QueryProvider.tsx:54` + `useServerFirstQuery.ts:63` (cache-first) → `refetchOnWindowFocus: false` (намеренно, «S3 Fix: less aggressive», чтобы снизить нагрузку/чтение Firestore).
- `BroadcastChannel` нет; `visibilitychange` только в `ThemeWatcher` (тема, не данные).
- Свежесть данных подтягивается ТОЛЬКО на: mount/навигацию (если stale >30s), reconnect, ручную кнопку «Обновить» (`series/page.tsx:112` refreshSeries), reload.

Вывод: «динамическая логика», которую хочет пользователь — это НЕ правка текста, а **архитектурная развилка про ДЕТЕКЦИЮ удалённых изменений данных**. Варианты:
- **A. Real-time `onSnapshot`** — данные синкаются живьём (как Google Docs), уведомление не нужно. Цена: больше чтений Firestore (биллинг), сложнее, ломает нынешнюю local-first/offline модель.
- **B. Refetch на фокус/`visibilitychange`** — вернулся на вкладку → подтянулось. Просто. Цена: больше чтений (это специально ВЫКЛючили ради нагрузки).
- **C. Лёгкий сигнал «данные могли устареть»** + ручной refresh (близко к текущему, но честно показать статус).
- **D. Дешёвый детектор**: один «last-updated» timestamp-док на пользователя (одна лёгкая подписка/поллинг) → «есть новые данные, обновить?» без полного real-time.

Крутить дальше: чего хочет пользователь — свежесть (живой синк) vs нагрузка/простота/стоимость. От этого путь.

### Firestore free-tier + «beacon» синк (ТРИЗ-разрешение, 2026-07-19)

**Лимиты Spark (free), сбрасываются ежедневно, midnight PT:** 50k reads/день · 20k writes/день · 20k deletes/день · 1 GiB storage · 10 GiB egress/мес. При превышении — приложение БЛОКИРУЕТСЯ (не биллится). Reads — самый дефицитный ресурс (синк жрёт именно reads). Free tier = НЕТ Cloud Functions (нужен Blaze) → beacon-bump делать клиентом.

**Противоречие (ТРИЗ, названо пользователем):** правки с телефона должны приходить (свежесть) ↔ нагрузка на Firestore минимальна (free tier).

**Разрешение (IFR — идея пользователя, валидна):** разделить ДЕШЁВУЮ ДЕТЕКЦИЮ и ДОРОГОЙ FETCH. Один крошечный «beacon»-док на юзера (`users/{uid}/meta/sync` с `rev`-счётчиком или updatedAt). На каждую запись данных — bump rev (+1 write, в том же batch). Клиент держит 1 onSnapshot на ЭТОТ один док (~1 read на реальное изменение) ИЛИ поллит на focus. rev вырос vs известного клиенту → invalidate React Query → refetch только затронутого списка (N reads ТОЛЬКО когда реально что-то менялось). Стоимость детекции = O(1), не O(N данных). Это НЕ литеральный хэш — проще: version-counter/serverTimestamp.

**Оценка под 100 польз/мес (реально ~15-30 DAU):** beacon ≈ 300 reads/юзер/день (детекция + редкие refetch) → ~9k/день на 30 DAU = ~18% от 50k. Даже наивный live-onSnapshot на полные списки ≈ 15k/день. Оба влезают с запасом; beacon двигает потолок до сотен DAU. Writes: +1/правку ≈ пренебрежимо vs 20k.

**Сложность: средняя.** Куски: (1) beacon-док + bump на КАЖДОЙ мутации (централизовать в data-слое, много мест), (2) хук-подписка на 1 док, (3) rev↑ → invalidate/refetch, (4) гранулярность: глобальный beacon (просто, refetch всё) vs per-collection rev (точно, больше учёта) — начать с глобального. Гейт free-tier: bump клиентом (нет Functions).

**ВАЖНО, честный caveat:** beacon чинит «вижу устаревшее» (read-freshness), но НЕ чинит десинхронизацию-перезапись, которую пользователь ловил (правка на 2 устройствах → одна перекатила другую). Это WRITE-конфликт (last-write-wins на whole-doc), ОТДЕЛЬНАЯ задача (field-level merge / версионирование / conflict-resolution).

### Прозрение (2026-07-19): resume token > ручной beacon; getDocs→onSnapshot; убрать двойной кэш

**Что в коде:** `firebaseClientDb.ts:34` — `initializeFirestore(localCache: persistentLocalCache({tabManager: persistentMultipleTabManager()}))` → встроенный IndexedDB-кэш ВКЛючён (полная локальная копия, multi-tab). НО читаем везде `getDocs` (bulk collection query, напр. `sermons.client.ts:108`) → при онлайне полный серверный read за весь набор на КАЖДЫЙ рефетч. Ни одного `onSnapshot`. Поверх — React Query со СВОИМ IDB-persister (`queryPersister.ts`, idb-keyval) → ДВОЙНОЙ кэш. `refetchOnWindowFocus:false`, staleTime 30s.

**Best practices (сверено с первоисточником):**
- Чтения из локального кэша НЕ биллятся (нет обращения к серверу = нет charge).
- **Resume token:** сервер отдаёт токен, клиент хранит в persistence; повторный запрос шлёт токен → сервер возвращает ТОЛЬКО изменившиеся с того момента доки → платишь только за дельту. Ничего не менялось → ~0 reads. Реализуется надёжно ЛИСТЕНЕРАМИ (`onSnapshot`); разовый `getDocs` online обычно перечитывает весь набор.
- Listener billing: initial = полный запрос; далее заряжается за added/updated; removed-because-changed заряжается; deleted — НЕ заряжается.
- Правило 30 мин: persistence ON + listener офлайн >30 мин → реконнект = полный запрос заново. (persistence OFF — при каждом реконнекте.)
- `onSnapshot` при persistence фаерит СНАЧАЛА из кэша (fromCache, мгновенно), потом из сервера.

**Вывод / «лучше, чем совет»:** мой прошлый `beacon` (ручной rev) = переизобретение resume token. Не строить его, а перейти getDocs→onSnapshot → «детекция + только дельта» бесплатно от SDK. Генерик-совет «listeners везде всегда» не идеален под нашу форму (однопользовательское, редко-пишущее, правило 30 мин на каждый список). ЛУЧШЕ под нас: cache-first мгновенный рендер (source:'cache'/persistence) + КОРОТКИЙ delta-sync листенером (resume token → платим только за правку с телефона) + снять дублирующий RQ-persist (Firestore уже персистит; RQ оставить как слой состояния/optimistic-мутаций). Это дешевле и проще, чем текущее, beacon, и listeners-везде.

**Как ложится на ТРИЗ:** resume token = SDK-нативное разделение «узнать что изменилось» ↔ «скачать только это» = наш IFR. Задача не строить, а перестать мешать SDK (уйти от разовых getDocs).

**Оговорки:** первый заход/подписка = полный набор (токен появляется после 1-го запроса); правило 30 мин = 1 полный read на холодный старт; НЕ чинит write-конфликт (перезапись с 2 устройств); миграция getDocs→onSnapshot = средняя, рискует задеть offline-мутации/RQ-потоки — не «включил и всё».

### Явная команда «Вставить как Markdown» (2026-07-19)

**Откуда родилось:** при фиксе вставки markdown (`09a69b68`) пришлось распознавать markdown-исходник эвристикой по тексту, потому что из буфера обмена намерение пользователя однозначно не читается. Эвристика сознательно консервативна → часть валидного markdown не конвертируется: одиночный `*курсив*` без второго маркера, Setext-заголовки (`Заголовок\n=====`), autolink'и, экранированные/вложенные формы. - Три локали (en/ru/uk), тесты на три состояния (Chromium-prompt / iOS-подсказка / установлено).

**Но схема «3.5 первой, 3.1 как fallback» лечит не ту болезнь. Четыре возражения.**

1. **Дневная квота не является узким местом.** Пик за 7 дней — 47 из 500, это 9.4%. Отказа по RPD, скорее всего, не было ни разу (в телеметрии не проверялось — открытая клетка).
2. **Раньше упрёмся в минутные лимиты, а не в дневной.** 4/15 RPM и 57.49K/250K TPM — минутные счётчики ближе к потолку, чем дневной. Вторая модель даёт +15 RPM и +250K TPM независимо, и вот это реальная польза; но она про всплеск одновременных запросов, а не про «квота на день кончилась».
3. **«3.5 мощнее» — предположение по номеру версии, и замер говорит обратное.** Обе модели одного лёгкого класса Flash-Lite, это не «старшая и младшая». Живой зонд 2026-09-07 (малая выборка, 11 запросов): `gemini-3.1-flash-lite-preview` — 5 успехов из 5; `gemini-3.5-flash-lite` — 4 из 6, дважды HTTP 503 «This model is currently experiencing high demand». Латентность обеих сильно скачет (0.6–56 с) — при `maxDuration: 60` на роутах (`vercel.json`) это само по себе риск. На платном тарифе 3.5 дороже: $0.30 in / $2.50 out против $0.25 in / $1.50 out у 3.1. **Пустая клетка: качество обеих на НАШИХ промптах никто не сравнивал.** Ставить 3.5 первой без такого сравнения нельзя.
4. **Наш код сегодня такую цепочку обычному пользователю не построит.** Механизм fallback есть: `structuredOutput.ts:111` `runWithFallback` идёт по списку targets, и 429 к нему допущен — `providerAdapters.ts:93` классифицирует 429 как `retrySameProvider`, а `structuredOutput.ts:124` пускает дальше всё, что не `terminal` (имя диспозиции при этом врёт: повторной попытки той же модели нет, сразу следующий target). Но сам список — это tier allowance: `tierPolicy.ts:156-159`, а у free `allowed = [configuredDefault]` (`tierPolicy.ts:30-33`), то есть цепочка из одного элемента и запасной модели нет. **Здесь спрятано смешение двух разных вещей:** наш внутренний tier — про монетизацию пользователя, квота Google — про доступность приложения. Fallback по 429 провайдера не должен зависеть от тарифа пользователя. Если делать вторую модель, разводить эти два понятия обязательно.

**Самый дешёвый ход — снять ограничение, а не строить обход.** Billing на проекте → Tier 1, и по обеим Flash-Lite: RPD 500 → 150,000, RPM 15 → ~4,000, TPM 250K → 4M (снято с той же страницы через «Compare tiers → Tier 1»). При нашем расходе счёт копеечный, а вся конструкция с двумя моделями, детекцией исчерпания и переключением просто исчезает вместе с кодом, который её обслуживает.

**Порядок, если браться:** сначала посмотреть в телеметрию, был ли хоть один отказ по дневной квоте → если ни одного, ничего не строить · страховка на будущее = billing, а не вторая модель · если всё же добавлять `gemini-3.5-flash-lite` в `functionCatalog.ts`, то вторым номером после 3.1, и до этого сравнить обе на реальных промптах.

## ❤️ Рабочая плоскость пастора — что стоит за сердечком (владелец, 2026-09-08)

**Контекст.** Сердечко в навигации ведёт на `/prayers`, и за ним сегодня только молитвенный журнал (`navConfig.ts:70-77`). Владелец: это должна быть **рабочая страница пастора** — «забота о сердцах», где молитвенный журнал лишь одна отдельная часть. Названы блоки: Посещения · Члены церкви · Нужды · Заботы/Проекты · и другое; голосом добавлено: молитва о ком-то, молитва о своих нуждах, посвящение, сложные вопросы.

**Ключевой факт из кода.** Все шесть блоков упираются в одну отсутствующую сущность: **человека в приложении нет**. Ни `Person`, ни `Member`, ни `Visit`, ни `Need` (`app/models/models.ts` — grep пуст). `Group` (`models.ts:313`) — это занятие, а не члены церкви; `PrayerRequest` (`models.ts:629`) не привязан ни к кому. Всё приложение организовано вокруг контента; эта плоскость — первая вокруг людей.

**Ключевой факт из поля.** Класс инструментов называется pastoral care software (Notebird, Undershepherd, TendFlock) и стоит отдельно от церковных CRM. Причина, по которой их бросают, одна и та же: ручное ведение списка. Слова пастора из кейса Notebird — «через неделю-две это прекращалось, потому что было не легко». Отсюда главный критерий фичи: **не что показать, а сколько ручного ввода нужно, чтобы страница осталась правдивой.**

**Три инварианта, без которых любой вариант умрёт:**
1. **Человек рождается из упоминания** — молитва «за Надежду, у неё операция» предлагает завести Надежду. Никакого «сначала заведи базу членов».
2. **Хранится след заботы, а не содержание разговора** — «был, помолились» да; что человек исповедал — нет. Это и совесть, и правовая сторона: письменные церковные записи защищены слабее самого разговора (clergy-penitent privilege покрывает беседу, не records).
3. **Пастор тоже под попечением** — посвящение и сложные вопросы стоят в той же плоскости. Ни один продукт в мире так не делает.

**Решение владельца (2026-09-08, после демо):** вариант **комнаты**; детализация отвергнута прямо — «детализация не будет работать, это точно». Про людей хранится минимум: дни рождения · кого посетил и кого ещё нет · короткая необязательная заметка о посещении. И рамка расширена: плоскость это не только забота о людях, а **внешняя память пастора** — «есть много такого, что пастору нужно помнить, но всё запомнить невозможно, и это было бы местом»: как совершать богослужения (похороны, венчание, крещение), проработанные ответы на сложные вопросы людей.

**Находка при переборе 35 кандидатов: у комнат три разные природы, и мешать их нельзя.**
- **Текущее** — люди, обход, нужды, даты жизни, молитвы. Меняется каждую неделю, нужен пульс «пора».
- **Вечное** — как совершать похороны, венчание, крещение; что делать в кризис. Пишется один раз спокойно, открывается в час, когда думать некогда. Делается редко — потому и забывается, и второго раза не будет.
- **Накопленное** — проработанные ответы, слово на случай, обещания. Растёт и переиспользуется.
- **Своё сердце** — посвящение, свои вопросы. В мире этого нет ни у кого.

**Состав плоскости (первый отбор, 7 комнат):** Люди · Обход · Нужды · Молитвенный журнал · Порядки служения · Когда беда · Сложные вопросы · Слово на случай · Обещания · Моё сердце. Отсеяно с причиной: записи «под дисциплиной» (самое чувствительное, чему в приложении не место) · статистика посещаемости и учёт десятины (превращают паству в метрику) · расписание проповедников, служения и хозяйственное (это администрация — календарь и группы).

**Стенд:** `frontend/.demo/pastor-plane.html` (`python3 -m http.server 8899` из `.demo`) — три экрана: плоскость с комнатами по этажам · конструктор из 35 кандидатов с тумблером беру/потом/мимо · комната изнутри на примере похорон. Полный разбор — `.sessions/SESSION_2026-09-08-pastor-working-plane-concept.md`.

**Открыто:** отбор владельца в конструкторе · слово на полях между «Нужды» и «Проекты» (прочитано как «Заботы») · «члены церкви» — вся община или личное попечение.

**Виток 3 (тот же день) — календарь, совет, типовое наполнение.** Владелец докинул: интеграция с календарём (посещения и праздники), дни рождения на месяц вперёд, комната-копилка тем к братскому совету, и принцип **«оформить типовое, а сверху уже добавлять»**.

Разведка дала один факт, меняющий конструкцию: **дату Пасхи у ЕХБ зашивать нельзя** — община сама выбирает григорианский или юлианский календарь, вопрос решается в общине или региональном объединении ([РИСУ / рекомендации ВСЦ ЕХБ](https://risu.ua/ru/pravlenie-vsc-ehb-obnarodovalo-rekomendacii-po-prazdnovaniyu-hristianskih-prazdnikov-po-novomu-stilyu_n130527)). Традиция выбирается в настройках, подвижные праздники считаются от неё. Праздник Жатвы — последнее воскресенье сентября или первое октября ([Союз ЕХБ](https://baptist.org.ru/news/main/view/article/1356889)). Братский совет избирается из служителей и **готовит предложения членскому собранию** ([устав](https://www.sbcnh.org/about/constitution/)) — значит копилка тем двухуровневая: к совету, а совет к собранию.

**Слом конструкции (Popper, свой контекст — независимость не засчитана): 8 попыток, 6 пробоин.** Подтверждено: одиннадцать комнат превращают плоскость во второй дашборд (лечение — свёртывание пустых за месяц комнат) и календарь Пасхи не универсален. Правдоподобно: чин похорон никто не напишет в спокойный день, холодный старт с пустыми комнатами, риск навязать чужую традицию готовым богословием (законен только скелет), реестр общины на телефоне. Выстояло: «человек рождается из упоминания» и «чем это лучше блокнота». **Идея владельца про типовое наполнение лечит сразу две пробоины из шести.**

**Этажи плоскости (итог витка):** Люди · **Церковь** (Календарь заботы · Совет и проекты) · Вечное (Порядки служения · Когда беда) · Накопленное (Сложные вопросы · Слово на случай · Обещания) · Своё сердце. Демо — пять экранов, 42 кандидата в конструкторе.

**Виток 4 — первый рабочий кусок (решение владельца, рисунком).** Три активные комнаты: **Люди · Посещения · Календарь заботы** — они связаны в одно и покрывают то, что пастор делает руками уже сейчас. Все остальные комнаты стоят на странице **пунктиром с меткой «скоро»** — видно направление, не мешает пользоваться. Категории (этажи) сохраняются. Переименование по требованию владельца: **«Обход» → «Посещения»** («обход» звучит как инспекция).

**Связка трёх:** одна запись о посещении даёт три следствия — у человека обновляется дата последней встречи, пересчитывается счётчик «кого ещё не был», в календарь уходит напоминание вернуться. Пастор не заполняет три места.

**Интеграция с календарём проверена по коду, а не обещана.** `calendar/page.tsx` уже собирает два независимых источника — `useCalendarSermons` и `useCalendarGroups` — каждый в свой `xByDate`, каждый со своим фильтром (`PreachCalendar.tsx:37-38`, чипы 260-278). Забота встаёт **третьим источником тем же способом**: `useCalendarCare` → `careByDate` → третий чип. Существующий календарь не трогается.

**Поправка владельца:** пунктир — это **состояние комнаты, а не её новое место**. Категории фиксированы (Люди · Церковь · Вечное · Накопленное · Своё сердце); недоделанная комната остаётся на своём месте и просто рисуется пунктиром с чипом «скоро». Карта плоскости не должна перетасовываться от релиза к релизу.

**Виток 5 — кликабельный прототип.** `frontend/.demo/pastor-plane.html` стал работающим прототипом: состояние в JS, роутер с крошками и «назад», localStorage, toast. Проверено живьём, что связка трёх комнат не нарисована, а работает: одна запись посещения меняет дату у человека, счётчик обхода (8/12 → 9/12) и календарь (событие «был» + напоминание «вернуться»). Фильтр «Забота» в календаре приложения гасится и оставляет ровно сегодняшний календарь.

**Виток 6 (2026-09-09) — концепция вынесена в отдельный документ.** Полная карта плоскости, очередность реализации и открытые вопросы теперь живут в **`PASTOR_PLANE_PLAN.md`** в корне репозитория; здесь остаётся только указатель. Очередность владельца: молитвенный журнал → люди → интеграция с календарём (дни рождения) → посещения → остальное. Раздел переименовывается (сейчас «Молитва»), варианты в §7 плана.
