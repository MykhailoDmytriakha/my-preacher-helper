### L1. Отказ в устаревшей записи (compare-and-swap по ревизии)
Новый общий примитив `conflictSafeUpdate(ref, aggregate, expectedRevision, patch)`:
внутри транзакции читаем документ → сравниваем `rev[aggregate] ?? 0` с ожидаемой → **не совпало = типизированный конфликт, записи НЕТ** → совпало = пишем patch + `rev.<aggregate> = n+1`.

Почему **не** `updatedAt`: см. §1. Почему **не** `atomicUpdate`: он пересчитывает операцию на свежих данных (правильно для add/remove), но НЕ сравнивает неизменяемую базовую ревизию редактора (`atomicUpdate.client.ts:28-72`). Это дополняющие примитивы, не конкурирующие.

Почему ревизия **на агрегат, а не на документ**: у проповеди в одном документе живут title, preparation, outline, scratch, thoughts, structure, dates. Одна общая ревизия дала бы ложные конфликты на несвязанных записях. Ключи-агрегаты: `core | outline | scratch | thoughts | structure | prep | dates`.

Миграция **не нужна**: отсутствующая ревизия читается как `0`, первая запись ставит `1`.

`prayerRequests.client.ts:73-94` · `sermons.client.ts:166-283` и `:354-411` · `planTemplates.client.ts:60-71`.

### L2. Осведомлённость — слушатель активного документа
`onSnapshot` на ОДИН редактируемый документ, живёт вместе с сессией редактора. Возвращает **только удалённую ревизию/снимок наружу редактора** — не трогает ни React Query, ни state редактора (иначе сотрёт черновик, см. `EditSermonModal.tsx:64-68`).
Отдельная плашка **рядом**, а не внутри `SwUpdateToast` (`layout.tsx:77-84`): у той свой смысл — «новая версия приложения» + перезагрузка (`SwUpdateToast.tsx:18-45`). Разные тексты, иконки, id тоста и действия.

**Конкретные тексты (ключ `freshness.*`, во всех трёх локалях — сейчас его нет ни в одной).**
Существующая плашка версии приложения (`pwa.updateAvailable`) говорит: «Доступна новая версия» / «Перезагрузите, чтобы получить последнюю версию приложения» / «Обновить». Новая обязана не пересекаться по смыслу:

| | версия приложения (есть) | данные (новое) |
|---|---|---|
| заголовок | Доступна новая версия | Данные изменились на другом устройстве |
| описание | Перезагрузите, чтобы получить последнюю версию приложения | Эта запись была отредактирована в другом месте |
| действие | Обновить (перезагрузка страницы) | «Показать новую версию» (редактор чистый) / «Посмотреть изменения» (редактор грязный) |

Ключевое различие для пользователя: первая перезагружает ПРИЛОЖЕНИЕ, вторая подтягивает ЗАПИСЬ и страницу не перезагружает.

### L1-БЛОКЕР: CAS без сохранения черновика — НЕ улучшение (найдено при проверке плана)

`useAutoSave` при размонтировании делает `debouncedSave.flush()` (`useAutoSave.ts:66-72`), а неудачу сохранения кладёт в `console.error` + `status='idle'` (`:47-53`) — **в UI она не попадает**, компонент уже уходит.

Сценарий: печатаю → ухожу со страницы → flush шлёт устаревшее → L1 отказывает → **текст не записан и отказ никто не увидел**. Сегодня он бы записался (затерев чужой).
То есть CAS сам по себе меняет «тихо затёр чужое» на «тихо потерял своё» — это НЕ строгое улучшение и именно то промежуточное состояние, которое хуже HEAD.

**Требование (не пожелание):** отказ по ревизии обязан ПЕРЕД отказом положить отвергнутый текст в переживающее перезагрузку хранилище (ключ = документ+агрегат+uid), а при следующем открытии документа предъявить его. Порядок внутри L1 строгий: **сначала сохранение отвергнутого черновика, потом включение отказа.** Обратный порядок — регрессия.

### L3. Восстановимость — черновик переживает выбор
- Редактор **чистый** → «Обновить» применяет удалённую версию.
- Редактор **грязный** → кнопка становится «Посмотреть изменения»; автосейв заморожен до выбора; обе версии сохранены.
- Устаревшее сохранение отвергается, **даже если пользователь плашку не видел**.

## 2б. Порядок выкатки (переписан; старый L0→L1→L2→L3 отменён)

**Правило:** ни один шаг не имеет права пройти состояние, где потерь больше, чем в текущем коде.

1. **Долговечный черновик — ПЕРВЫМ и отдельно.** Ключ `uid + документ + агрегат`; правка ложится в хранилище, переживающее перезагрузку, ДО попытки записи; восстанавливается при следующем открытии. Это единственный шаг, который уже сам по себе двигает «никогда молча не терять текст» — он закрывает и падение вкладки до срабатывания задержки (заметка отменяет отложенное сохранение при размонтировании, `studies/[id]/page.tsx:226`: напечатал и закрыл в пределах 1,5 с — текста нет уже СЕГОДНЯ).
2. **Хирургические патчи полей** (четыре отклонившиеся точки). Может ехать в одиночку, снижает риск, но НЕ является границей корректности.
3. **Протокол для ВСЕХ писателей одного агрегата** — клиент, API, Admin, офлайн-доигрывание, удаление, много-агрегатные операции; рубеж версии клиента.
4. **CAS и интерфейс разрешения конфликта — ОДНИМ неделимым релизом.** CAS в одиночку не выкатывать никогда.
5. **Слушатель — последним**, и до успешного серверного снимка состояние показывать как «неизвестно», а не «свежо».
6. Повторить по сущностям с явной матрицей приёмки.

Пункт 1 берём в работу сейчас. Пункты 3-4 — только после того, как 1 закрыт и проверен живьём.

## 2в. СДЕЛАНО: шаг 1 «долговечный черновик» (2026-07-25)

`frontend/app/utils/durableDraft.ts` + `frontend/app/hooks/useDurableDraft.ts`, подключено к редактору заметки; ключи `unsavedDraft.*` в трёх локалях; 24 теста (11 на хранилище, 13 на хук).

**Инвариант:** черновик в хранилище существует ⟺ есть текст, который сервер не подтверждал. Отсюда «предложить восстановить» однозначно, а не назойливо.

**Что закрывает.** Текст, набранный и не доживший до сохранения: закрытие вкладки, уход со страницы (у заметки отложенное сохранение ОТМЕНЯЕТСЯ при размонтировании — `studies/[id]/page.tsx:225-232`), сворачивание приложения на телефоне, падение. Пишется до попытки записи, снимается только успехом.

**Три дыры прежнего образца (`prep-draft-backup-<sermonId>`), которые закрыты:** ключ теперь включает uid (на общем компьютере следующий аккаунт не прочитает чужой текст); восстановление ПРЕДЛАГАЕТСЯ, а не применяется молча; пишется при наборе, а не только при попытке сохранения.

**Дефект, найденный ЖИВОЙ проверкой (юнит-тесты его не видели).** Первая версия писала черновик при каждом уходе со страницы, даже когда всё сохранено. Выглядит безобидно — черновик равен содержимому, полоса не всплывает — ровно до момента, когда тот же документ правят на другом устройстве: тогда залежавшийся черновик начинает ОТЛИЧАТЬСЯ от свежего серверного текста, и редактор предложит восстановить СТАРОЕ поверх НОВОГО. То есть я воспроизвёл бы ту самую беду, за которую критиковал старый образец. Лечение — понятие «подтверждённое сервером значение»: значение, с которым редактор открылся, считается подтверждённым, пишется только отличающееся. Закреплено двумя тестами.

**Проверено живьём** (localhost, тестовый аккаунт, заметка `866afb86…`, удалена после проверки): детектор на запись в хранилище поймал `SET` с набранным текстом и `DEL` через 1156 мс после подтверждения сервером · полоса «Найден несохранённый текст» показалась при заходе с посаженным черновиком · «Восстановить» вернуло текст, и он доехал до базы (пережил перезагрузку) · после простого посещения без правок черновик НЕ остаётся.

**Методическая ловушка, стоившая трёх попыток.** Посадить черновик и тут же перезагрузить страницу НЕЛЬЗЯ: перед выгрузкой срабатывает собственный обработчик и пишет поверх текущее состояние редактора. Сажать нужно из вкладки, где редактор НЕ открыт.

### ⚠️ ГЛАВНЫЙ УРОК ВИТКА: ориентир диффа — «с чем открылись», а НЕ «что сейчас в кэше»

Первая версия шага 2 сравнивала состояние редактора с **живым кэшем**. Выглядит естественно и **уничтожает данные** — проверено живьём, две вкладки на одной заметке:
1. вкладка A правит заголовок → в базе новый заголовок;
2. вкладка B (открыта раньше, в поле у неё СТАРЫЙ заголовок) при получении фокуса подтягивает кэш → в кэше уже новый заголовок;
3. B правит текст → дифф видит `кэш.заголовок ≠ поле.заголовок` и считает нетронутый заголовок **намеренным переименованием обратно**;
4. итог в базе: правка A **уничтожена**. Подтверждено чтением через Admin SDK.

Правильный ориентир — значение, с которым редактор **открылся** (далее — подтверждённое сохранением). Он отвечает ровно на нужный вопрос: «что трогал пользователь». Мой прежний довод в пользу кэша («самоисцеление после неудачной записи») оказался ложным: поле, которое пользователь действительно менял, остаётся отличным от ориентира открытия, пока запись его не унесёт, — самоисцеление то же самое.

Правило вынесено в общий `frontend/app/utils/changedFields.ts` (8 тестов, проверено мутацией) и применяется и в заметке, и в группе. **Повторный живой опыт после исправления: обе правки выжили** — заголовок от A и текст от B.

Тот же ориентир уже используется в долговечном черновике (`confirmedRef`) — это одно понятие, а не два.

**Побочная находка (была в коде и до правки, занесена в BUGS.md).** Автосейв группы читал значения из refs, полагаясь на то, что первой строкой ВСЕГДА идёт `await` записи группы — эта случайная уступка планировщику давала React зафиксировать состояние. Когда запись стала пропускаться при отсутствии изменений, уступка исчезла, и дата встречи читалась пустой (`date=""`, подтверждено логом). Поставлен явный `await Promise.resolve()` с объяснением.

**Едва не внесённая своя регрессия — откатил.** Хотел снимать черновик предыдущего ключа при смене документа, чтобы убрать осиротевший черновик временного идентификатора. Но ключ меняется и при переходе с заметки на заметку БЕЗ размонтирования хука — то есть код удалял бы несохранённый черновик покинутой заметки. Временный черновик снимается там, где это осмысленно: в редакторе заметки в момент присвоения настоящего идентификатора.

## 4. Ловушки, которые обязаны быть закрыты кодом (не «учтены»)
- Собственная запись поднимает событие слушателя → подавлять свои ревизии и `hasPendingWrites`, иначе плашка на каждый автосейв.
- Автосейв против «Обновить»: у заметки debounce 1.5 с, у групп/структуры 500 мс (`studies/[id]/page.tsx:226-232`, `usePersistence.ts:100-120`) — отложенное сохранение после обновления воссоздаёт исходный баг.
- Flush при размонтировании пишет устаревший state уже после ухода со страницы (`useAutoSave.ts:65-72`, `usePersistence.ts:137-160`).
- Офлайн: транзакция офлайн не работает → устаревшую полнополевую запись НЕЛЬЗЯ слепо ставить в очередь; нужен локальный intent + сверка при реконнекте.
- Две очереди уже есть: Firestore multi-tab (`firebaseClientDb.ts:28-36`) и persisted-мутации React Query (`QueryProvider.tsx:78-93`) — нужно ОДНО правило владения, не двойной replay.
- Загрязнение кэша между аккаунтами: глобальный ключ персистера (`queryPersister.ts:7-26`), ключ проповеди без uid (`useSermon.ts:58-68`) — чинить ДО того, как слой свежести начнёт доверять восстановленному кэшу.
- Жизненный цикл слушателя: отцепить на unmount/смене документа/смене uid/логауте; ошибка прав завершает слушателя навсегда → показать «свежесть недоступна», а не молча зелёный.
- Стоимость: один слушатель активного документа дёшев; подписка через каждый list-hook — нет.
- Удаление против офлайн-правки: «удалено на другом устройстве против твоего черновика», не молчаливое воскрешение.

## 5. Критерии приёмки (проверяемые, не «сделано»)
1. Две вкладки, одна заметка, правки в РАЗНЫЕ поля → обе выживают (L0).
2. Две вкладки, ОДНО поле → второе сохранение **отвергнуто**, текст второй вкладки не потерян, показан конфликт (L1+L3).
3. Правка в другой вкладке при открытом чистом редакторе → плашка с текстом про ДАННЫЕ (не про версию приложения) (L2).
4. Плашка про новую версию приложения по-прежнему отличима и работает.
5. Собственный автосейв плашку НЕ поднимает.
6. Повторить 1-3 ещё на двух типах сущностей (проповедь, группа/серия).
7. Замер чтений: сколько документов в день на активного пользователя, укладываемся ли в бесплатный лимит при 100 пользователях.

## 5a. Цена (предварительная арифметика, подлежит замеру)

Правила безопасности проверяют только владение, без белого списка полей (`firestore.rules:30-58`) → поле ревизии проходит, правила менять не нужно.

**L1 CAS — нулевая дельта по чтениям.** Текущий путь и так читает перед записью (`studies.service.ts:143` — `getDoc`→`updateDoc`). Транзакция читает столько же. Ревизия пишется тем же патчем, отдельной записи нет.

**L2 слушатель — примерно 1 чтение на открытие документа** (первичная выдача; изменения — по документу за изменение; отдача из кэша не тарифицируется).

Оценка на 100 пользователей: 20 открытий документов в день = 2 000 чтений; 50 сохранений в день = 5 000 чтений + 5 000 записей. Итого ≈ 7 000 чтений при лимите 50 000 и 5 000 записей при лимите 20 000 — **порядка 14 % и 25 %**. Запас есть, но замер (критерий 7) обязателен: оценка не факт.

## 6. Что останется нерешённым осознанно
Офлайн-правка без durable outbox; падение до срабатывания debounce; автослияние одинакового текста (CRDT — намеренно НЕ берём: цена несоразмерна для личного приложения с редкой одновременной правкой).
